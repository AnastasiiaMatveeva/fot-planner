# Защита демонстрации: сервис планирования ФОТ

Показ 10.09.2026. Файл — опора для выступления: что это за сервис, как он
устроен, что показать и в каком порядке, какие числа должны появиться на
экране, как отвечать на трудные вопросы. Всё, что здесь написано, проверено
ночью 09–10.09 сквозным прогоном (`scripts/demo_run.py`); числа взяты из
него.

---

## 1. Одной страницей: что это

**Задача.** Экономист планово-экономического отдела каждый год раскладывает
фонд оплаты труда по договорам: кому, с какого договора, в каком месяце,
каким видом выплаты. Правил десятки: сроки договоров и сроки выплат, касса
по месяцам, приказ № 2556 (предел оклад + 122), П4 (предел при надбавке за
интенсивность), БЭП по ГОЗ (средняя штатная часть), трудоёмкость из РКМ
(человеко-месяцы и стоимость), число специалистов на строке, совместительство
и его пределы, замещение должностей, категории занятости, приоритет 2030,
надбавка за гостайну. Вручную в Excel это недели работы и всегда «примерно».

**Что делает сервис.** Экономист загружает документы как они есть (штатное
расписание, договоры, РКМ по ГОЗ, структуру цены гранта, приказы). Агенты
читают их и складывают в реестр организации. Решатель (математическая
оптимизация, MIP) строит помесячный план выплат, в котором все жёсткие
правила выполнены, а «вкусовые» цели (меньше переводов, меньше дробления,
равномерное освоение) минимизированы. Отчёт — в формах экономистов,
четырнадцать разделов, плюс проверка каждого правила по готовому плану.

**Чем не является.** Не проводит платежи, не заменяет кадровый учёт и
бухгалтерию, не «придумывает» правила: каждое правило — из приказа,
положения или слов экономистов, и на каждое есть проверка.

**Ключевая мысль для показа.** Три слоя, и каждый проверяем:
документ → строка реестра (видно, откуда взято) → правило решателя
(видно, соблюдено ли) → отчёт (видно, что вышло).

## 2. Как устроено

### 2.1 Реестр организации

Общая база организации, не одного плана: договор живёт несколько лет,
штатка меняется приказами. Вкладки реестра: Документы, Договоры, Штатное
расписание, Трудоёмкость, Поступления, Надбавка 120, Справочник должностей,
Правила замещения.

Каждая строка реестра помнит документ-источник. Удалили документ — ушли и
его строки. Повторная загрузка файла с тем же именем — новая версия, старые
строки уходят из расчёта, файл и переписка остаются. У файла есть отпечаток
(SHA-256): подменить источник задним числом нельзя, тот же файл под другим
именем сервис назовёт вслух.

Что в реестре «годовое», а что приходит с планом:

| Раз в год (нормативная база) | С каждым планом (документы экономиста) |
| --- | --- |
| Положение об оплате труда (оклады по должностям) | Штатное расписание (люди, ставки, зарплаты, категории, запреты договоров, лист 120) |
| Приказ № 2556 (пределы оклад + 122) | Договоры (сроки, счета, ФОТ, разрешённые выплаты, ГОЗ, приоритет, подразделение) и поступления по месяцам |
| Справка П4 (предел при 124) | РКМ по ГОЗ (форма 9д: должности, чел.-мес., стоимость, число специалистов; форма 22: БЭП) |
| Письмо о БЭП (550 ВП МО РФ) | Структура цены гранта («Расшифровка ФОТ» по этапам с датами) |
| Правила замещения должностей (должности.xlsx) | |

Справочник должностей (оклад, П2556, П4, БЭП по каждой должности) — один
файл с шаблоном входа решателя (`docs/ui/demo_input.xlsx`, лист
`лимиты_по_должностям`): правка попадает в расчёт без промежуточных копий.
У каждой величины справочника есть документ-источник: оклад — положение
об оплате труда, П2556 — приказ № 2556 (основание и дата действия
извлечены агентом), П4 — справка П4 2025, БЭП — письмо 550 ВП МО РФ.
Связь видна над таблицей справочника (вкладка «Справочник должностей»),
в карточке документа («источник для: П4») и уходит в основание каждого
расчёта (лист «источники» выгрузки, раздел 13). Ставится агентом при
записи величин из документа или экономистом вручную; справка П4 — скан
без текстового слоя, письмо о БЭП — с нечитаемым слоем, поэтому их
величины внесены рукой, а связь поставлена явно.

### 2.2 Агенты

Агент здесь — короткая операция с началом, концом и следом в базе. Экономист
видит не «идёт обработка», а кто именно работает, сколько заняло и что
вышло. Страница «Ход работы» показывает след по каждому документу.

| № | Агент | Что делает | Работает |
| --- | --- | --- | --- |
| 1 | Извлечение данных | определяет вид документа, читает его (шаблонные формы — сам, по листам; остальное — моделью), кладёт строки в реестр; спорное — на подтверждение экономисту | да |
| 2 | Настройка расчёта | переводит фразы экономиста в переменные решателя: закрепить/запретить человека на договоре, допуск трудоёмкости, дефицит, число договоров оклада; претензии к плану — в веса целей | да |
| 3 | Анализ невыполнимости | когда решения нет — читает отказ решателя, сверяет с реестром, ставит опыты с одним ослабленным условием и называет цену выхода («сходится, если допустить дефицит: столько-то с такого-то месяца») | да |
| 4 | Сценарное моделирование | «что будет, если» тем же решателем | да |
| 5 | Сверка плана и факта | приём фактических начислений | **нет — заготовка, интерфейс так и говорит** |
| 6 | Пояснительные материалы | записка по числам расчёта | да |
| 7 | Нормативная база | читает приказ/положение/справку, сверяет со справочником должностей, показывает расхождения; пишет только после подтверждения | да |
| 8 | Проверка результата | пересказывает предупреждения решателя по готовому плану | да |

Языковая модель отвечает только за чтение текста и за слова в ленте. Куда
положить прочитанное, что считать, что записать — решает код сервиса. В
расчёт данные попадают только из реестра.

### 2.3 Решатель

Модель смешанного целочисленного программирования (Pyomo + HiGHS).
Переменные: ставка человека на договоре в месяце (шаг 0,25), сумма каждого
вида выплаты, отнесение человека на строку РКМ. Жёсткие правила — как
ограничения; предпочтения — стадиями: сначала минимизируется отклонение
трудоёмкости, его результат фиксируется, затем следующая цель, и так до
взвешенной стадии (переводы, административная сложность, равномерность,
стабильность сумм). Веса взвешенной стадии экономист двигает словами в
чате («слишком много переводов»).

Правила, которые сервис проверяет по готовому плану независимо от
решателя (вкладка «Контроль расчёта»), — это и есть перечень бизнес-правил;
он же ниже в разделе 5.

### 2.4 Контур качества

Тесты решателя в `tests/` отключены (устарели после переработки модели
выплат); вместо них два стенда:

* `harness/run.py` — стенд разбора документов: по каждому известному документу
  проверяет вид, число строк, обязательные строки и то, чего быть не должно
  (человек из примера в приказе, принятый за сотрудника). Приговоры
  экономиста предложенным строкам («принять»/«отклонить») автоматически
  становятся случаями стенда — это и есть самообучение в честном виде:
  модель не переучивается, но каждая ошибка после исправления сторожится.
* `harness/crisis.py` — 30 кризис-тестов правил решателя на маленьких входах,
  по одному правилу каждый, плюс инварианты, которые обязаны выполняться в
  любом плане (зарплата целиком, шаг ставки, 122 при окладе, П2556, П4, БЭП,
  152, приоритет, касса, сроки).

## 3. Как пользоваться (по экрану)

**Запуск.** Сервер: `.venv/Scripts/python.exe -m uvicorn main:app --app-dir app --host 0.0.0.0 --port 8770`
(или конфигурация `app` из `.claude/launch.json`). Адрес: `http://127.0.0.1:8770`,
с другого компьютера в сети — `http://192.168.140.44:8770`. Модель разбора —
из `.env`: `FOT_LLM_PROVIDER=deepseek` (внешняя) или `local` (vLLM на
сервере организации, для ГОЗ).

**Левая колонка.** «Текущий план» — последний посчитанный план сразу
сводкой. «Реестр организации» — общая база. Ниже список планов, внизу
«+ Новый план».

**Реестр организации → Загрузить документы** (кнопка или перетаскивание).
Файлы уходят агенту; в ленте плана видно, как он их определяет и читает.
Вкладки реестра показывают, что из них вышло. Клик по имени документа —
карточка: сам документ (как напечатан), извлечённые строки, переписка о
документе («тут ошибка» — агент правит и запоминает), предложенные строки
с оценкой «надёжно / проверить / сомнительно» и кнопками принять/отклонить.

**Лента плана.** Реплики агентов и экономиста. Здесь же вопросы агента
(например, «поступления не равны ФОТ договора — что принять?») и
предложение считать, когда данных достаточно.

**Рассчитать план.** Перед запуском — окно намерения: сколько сотрудников,
договоров, поступлений, строк трудоёмкости, надбавок 120, правил замещения,
закреплений и запретов уйдёт в расчёт, какие допущения сервис принял за
экономиста (например, «графика поступлений нет — фонд разложен ровно по
месяцам»). Расчёт идёт в фоне; в ленте появляются строки работ решателя и
агента проверки.

**Вкладка «План ФОТ».** Разделы отчёта:
1 Итоги · 2 Договоры · 3 Освоение · 4 Касса · 5 Виды выплат · 6 Выплаты
(6.1 помесячно по людям, 6.2 регистр по периодам, 6.3 «ШР на дату,
детализация назначений» — форма отдела кадров, те же 23 графы, что в их
шаблоне) · 7 Ставки · 8 БЭП · 9 П4 · 10 Трудоёмкость ·
11 Исполнители · 12 Нехватка · 13 Расчёт (версии, цели и настройки) ·
14 Дефицит · 15 Контроль расчёта (каждое правило: соблюдено / нарушено /
не применялось, с числами). Переключатель разделов — строкой под панелью
действий, у раздела с замечанием точка (жёлтая — внимание, красная —
нарушение). У таблиц
автофильтр как в Excel. В панели над отчётом одна строка: версия расчёта
(рядом корзина — удалить неудачную версию; данные реестра не трогаются),
«Период» — месяцы, «Масштаб» — размер таблиц, скачать Excel, на весь экран.
В «Итогах» у каждого замечания кнопка «Перейти» — открывает нужный раздел
на нужной строке и месяце (для всех видов замечаний: касса, П4, БЭП,
трудоёмкость, дефицит, договоры).

**Чат.** Реплика появляется в ленте сразу, под ней — три точки: агент
отвечает (обычно 3–6 секунд). Агент опирается только на состояние плана:
если числа там нет, он говорит «в состоянии плана этого нет», а не
придумывает. На возражение экономиста он разбирает вопрос заново, а не
защищает прежний ответ.

Фразы, которые сервис понимает и выполняет (не «отвечает», а делает):
* «оставь Петрова на гранте с июня по декабрь» — закрепление, пересчёт;
* «Сидорову на ГОЗ не сажать» — запрет; «сними закрепление Петрова»;
* «допуск трудоёмкости 10 %», «разреши дефицит», «не больше двух договоров оклада»;
* «слишком много переводов», «освоение рваное» — претензия к плану: вес цели ×2, пересчёт, в ленте — что сдвинулось против прошлой версии;
* «договор 1234 — это ГОЗ», «у Петрова оклад 90 000» — правка поля реестра;
* «не бери прошлогоднюю штатку» — исключить документ из расчёта;
* «почему Иванову открыли полторы ставки?» — ответ по посчитанным причинам («Почему так»).

**Скачать результат.** Кнопка у версии расчёта — Excel с листами
«Итог расчёта», «Проблемы и предупреждения», «План выплат», «ФОТ по
договорам», «Контроль трудоёмкости», «ШР_детализация», «цели»,
«открытые_ставки», «источники» (какие документы и версии агентов легли в
основание расчёта).

## 4. Сценарий показа (30–40 минут)

Числа ниже — из ночного прогона того же набора; при живом расчёте они
могут отличаться в мелочах (решатель выбирает один из равноценных планов),
но состав видов выплат, разделы и проверки — те же.

**0. До показа (5 минут).** Открыть `http://127.0.0.1:8770`. В левой колонке
уже есть посчитанный «План ФОТ на 2026 год» — запасной вариант. Открыть
«Реестр организации» → «Документы»: там только нормативная база (положение
об оплате труда, приказ № 2556, справка П4, письмо о БЭП, правила
замещения). Это «то, что меняется раз в год».

**1. Что уже знает сервис (3 минуты).** Реестр → «Справочник должностей»:
оклад, П2556, П4, БЭП по каждой должности — их принесли нормативные
документы. «Правила замещения»: 30 направленных правил из файла
экономистов («Главный инженер проекта → Инженер, Ведущий инженер»).
Открыть карточку приказа № 2556: видно, что агент нормативной базы
извлёк, с чем сверил, где расхождения. **Справка П4 2025** прочитана по скану: средние за 2025 год НР 280 023,62 и
НТП 162 648,30; агент делит их на 1,086866 (отпускные, правило экономистов
из «справочная информация_ЗП.xlsx») и получает 257 643,19 и 149 648,90 —
ровно то, что стоит в справочнике: расхождений нет. Письмо о БЭП тоже
прочитано по скану: 112 261 на 2025 год, сходится.

**2. Новый план и документы (5 минут).** «+ Новый план». В реестре нажать
«Загрузить документы», выбрать четыре файла из `data/demo/`:
`Штатное расписание 2026.xlsx`, `Договоры 2026.xlsx`,
`РКМ ГОЗ Радар-26.xlsx`, `Структура цены Грант-26.xlsx`. Вернуться в
ленту плана: агент определяет вид каждого файла и читает его. Через
1–2 минуты в ленте: «Разобрал … сотрудников 10, надбавок 120 2»,
«договоров 5, поступлений 24», «строк трудоемкости 3»,
«строк источника 4 → позиций плана 2», «Данных достаточно для расчета».
Показать вкладки реестра: Штатное расписание (10 человек, у Волковой
«запрещены: C_GOZ-26», категория «студент», у Орлова ставка 0,5),
Договоры (сроки, счета, ГОЗ, признак «Приоритет», разрешённые выплаты,
предел выплат ГОЗ 31.10.2026), Поступления (полосы по месяцам: у каждого
договора свой график — ГОЗ тремя траншами, грант двумя, коммерция и
приоритет кварталами), Трудоёмкость (строки Ф9 с числом специалистов и два
этапа гранта с датами), Надбавка 120 (Кузнецов по ГОЗ и Смирнова по
приоритету, по 5 %).
Открыть карточку РКМ: документ как есть и что из него извлечено, подсветка.

**3. Расчёт (около двух минут — можно показывать вживую).** «Рассчитать план» → окно намерения:
10 сотрудников, 5 договоров, 24 поступления, 5 строк трудоёмкости,
2 надбавки 120, 30 правил замещения; допущения сервиса: «разрешены только
эти виды выплат» и перенос человеко-месяцев ГОЗ в месяцы выплат. Запустить. Пока считает — показать «Ход работы»: кто из
агентов что делал, сколько секунд, версия агента. Рассказать про стадии
решателя (раздел 2.3). Время расчёта — см. раздел 4а.

**4. Результат (15 минут).** Вкладка «План ФОТ».
* 1 Итоги: ФОТ 15 540 000 ₽, выплачено 14 793 893 ₽, не освоено 746 107 ₽ (излишек денег — он и должен остаться).
* 2 Договоры: ГОЗ платит март–октябрь (предел выплат), грант — май–декабрь, коммерческий — только он даёт 124, приоритет — только он даёт 152.
* 5 Виды выплат: оклад, 122, **120 — гостайна** (Кузнецов с ГОЗ, Смирнова с приоритета и гранта — надбавка идёт с того договора, где оклад), **124 — интенсивность** (C_COM: Сидорова и Орлов), **152 — дополнительная работа** (C_PRI: Морозов), **стимулирующая приказом** (C_BASE — Волкова и Кузнецов, кому иначе не добрать до зарплаты).

## 6. Трудные вопросы и ответы

**«Это настоящие документы или подстроенный пример?»** Документы демо
сгенерированы заново скриптом `scripts/create_demo_docs.py` в формах,
которые присылают экономисты: штатное расписание, договоры с графиком
поступлений, РКМ по ГОЗ (в бланке формы 9д приказа ФАС № 995/22),
структура цены гранта («Расшифровка ФОТ»). Организация, люди и договоры
вымышленные; должности, оклады, пределы П2556/П4/БЭП и правила
замещения — настоящие, из нормативных документов и файлов экономистов
СПбПУ. Состав подобран так, чтобы в одном плане сработали все правила
(раздел 5), а расчёт уложился в две минуты: десять человек, пять договоров
разных видов, все шесть видов выплат.

**«Почему 124 почти не используется, фонд C_COM не освоен?»** Правило
экономистов от 04.09: П4 — норма, а не потолок. В месяце со 124 сумма
оклад + 122 + 124 равна ровно П4 × ставка (149 648,90 на ставку). Значит
124 получает только тот, чья зарплата не меньше П4 × ставка: Сидорова
(160 000) и Орлов (ровно П4 × 0,5). У остальных зарплата ниже предела —
им 124 назначить нельзя, и решатель обходится окладом и 122. Если П4
всё-таки потолок («не выше»), это правка одной строки в решателе — надо
подтвердить у экономистов.

**«Языковая модель может ошибиться — и в ГОЗ уйдёт неверная цифра?»**
Модель не пишет в расчёт. Шаблонные формы (штатка, договоры, РКМ форма 9д,
«Расшифровка ФОТ») читаются кодом по листам и графам, модели там нет. Модель
читает произвольные документы, и всё, что она прочла, ложится в
«предложения» с оценкой и ждёт подтверждения экономиста. Каждая строка
реестра помнит источник; у документа есть отпечаток. Приговоры экономиста
становятся случаями стенда: ошибка, исправленная один раз, сторожится всегда.

**«Документы по ГОЗ уходят во внешнюю модель?»** Провайдер задаётся одной
строкой `.env`: `FOT_LLM_PROVIDER=local` — модель на сервере организации
(vLLM, `192.168.150.188`), наружу ничего не уходит. Внешняя модель включена
сейчас только для демо-стенда.

**«Сколько считает и что будет на 100 человек?»** Демо (10 человек,
5 договоров, 12 месяцев, девять стадий целей) — около двух минут, статус
OPTIMAL. Модель растёт с числом людей × договоров × месяцев × видов выплат,
но растёт не так быстро, как кажется: главное — не заводить переменные там,
где договор человеку не разрешён. Графа «разрешённые договоры» в штатке
режет модель сильнее любой другой настройки.
Резервы известны и не использованы: параллельные потоки HiGHS, укрупнение
шага ставки, меньше стадий целей, разбиение по подразделениям. Промышленный
масштаб потребует замера и этих доработок — это честный ответ.

**«А если решения нет?»** Сервис не молчит: агент невыполнимости называет
правило, которое не сошлось, сверяет с реестром (есть ли вообще человек с
такой должностью, действует ли договор в эти месяцы, сходится ли стоимость
чел.-мес.) и ставит опыты: «сходится, если допустить дефицит — столько-то с
такого-то месяца». Вариант «дефицит» показан в разделе 4.

**«Откуда правила? Кто их подтвердил?»** Приказ № 2556, справка П4, письмо
о БЭП, положение об оплате труда — в реестре, и агент нормативной базы
сверяет их со справочником. Правила решателя записаны словами в
`docs/MODEL_REVIEW.md`; открытые вопросы к экономистам там же, пронумерованы,
в модель не зашиты. Правило замещения — из `должности.xlsx` экономистов
(направленное: «вниз можно, вверх нельзя»).

**«Тесты есть?»** Юнит-тесты решателя отключены — они описывали прежнюю
модель выплат, и «подогнать» их под код молча значило бы закрепить
неподтверждённые правила. Вместо них два стенда (раздел 2.4) и проверка
каждого правила по готовому плану (раздел 15 отчёта): проверяется не
«решатель сказал OPTIMAL», а «правило экономиста соблюдено, вот числа».

**«Что не сделано?»** Сверка плана с фактом (агент 5 — заготовка, интерфейс
говорит об этом). Сканы без текстового слоя читаются картинками через
модель с распознаванием — качество зависит от скана. Запрет 124 на ГОЗ —
устное правило, в модель не зашито до подтверждения. Лист «фиксация
поступлений» читается, но не применяется — правило не определено.

**«Почему не 1С / не Excel?»** Excel — это и есть вход и выход; сервис
добавляет то, чего в Excel нет: доказуемо допустимый план по всем правилам
сразу, след от документа до цифры, объяснение отказа и разговор с планом
словами.

3. Реестр чистый: во вкладке «Документы» только нормативные документы и `должности.xlsx`; демо-файлов нет (`scripts/demo_run.py --reset` удаляет их и демо-планы, потом прогоняет заново — 10–15 минут).
4. Файлы для загрузки руками лежат в `data/demo/` (четыре файла), вариант с дефицитом — в `data/demo_variants/дефицит/`.
5. Уже посчитанный план — основной вариант показа результата: «План ФОТ на 2026 год», последний прогон; запасные — два плана «Архив: …» на прежнем наборе из четырёх договоров. Живой расчёт — около двух минут, его можно показать целиком.
6. Расчёт не прерывать остановкой сервера: фоновый прогон останется «идёт».

## 8. Если что-то пошло не так

* **Модель недоступна** (нет сети): шаблонные формы всё равно читаются сами; лента скажет «модель недоступна», разбор произвольных документов и чат словами не работают. Показывать по готовому плану.
* **Разбор назвал документ «иное»**: для книг по шаблону сервиса это исключено (вид определяется по листам); для прочих — в чате «это документ по договору», агент переразберёт.
* **Расчёт долго**: нормальное время — около двух минут; если дольше, показывать реестр, карточку документа, ход работы, готовый план. Останавливать сервер во время расчёта нельзя: прогон пометится «прерван».
* **Решения нет** там, где ожидался план: открыть ленту — агент невыполнимости называет причину; чаще всего это поступления ≠ зарплаты в каком-то месяце.
