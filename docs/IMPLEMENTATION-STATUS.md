## Checkpoint L0.2 — защита достоверности исходных проверок

Дата: 11.09.2026. Поручение: продолжить практические улучшения по ТЗ.
До завершения полной инвентаризации выделена узкая исправляющая часть QA-003:
старый CLI мог списать аварийное завершение на known_red, а Stop и CLI
по-разному трактовали один вывод. Исправление этой ошибки существующей
приёмки не требует новых моделей БД и не означает прохождения зависимостей
L1/L2 или готовности L3 целиком.

Requirement IDs: `FOT-HARNESS-TZ-001/QA-003` — частично реализован;
`QA-002`, `DOC-002` — ограниченные свидетельства текущего CLI.

Изменения:

- `scripts/check_results.py`: единый анализ кода возврата и протокола для CLI
  и Stop; отдельные runtime/evaluation/acceptance, известные случаи сохраняют
  `failed`, разработческий итог — максимум `baseline_compatible`.
- `--strict` не прощает known_red. Пустой набор — `not_run`. Ошибки запуска,
  несогласованные счётчики/коды, незавершённый вывод и traceback блокируют
  приёмку. Номер known_red относится только к crisis, а не ко всем стендам.
- `--report PATH`: атомарно записываемый JSON с областью запуска, run_id,
  командами, временем, exit code, случаями и SHA-256 вывода/точки входа.
  Сырые выводы стендов, `.env` и содержимое документов в него не включаются.
- 22 регрессии в `scripts/test_check_results.py`, подключённые через parts
  к quick, выборке изменений, Stop и CI; не через отключённый pytest.
- CI настроен на строгий quick и сохранение JSON-артефакта даже при провале.
  Сам GitHub job локальным прогоном не проверяется: до push он `not_run`.
- При недоступном git режим changed/quick не начинает обращаться к LLM.
