## 1. Основание и цель

Утверждённый demo-ui реализует реальные сценарии экономического отдела: документы организации, годовые планы ФОТ, распределение выплат по сотрудникам и договорам, трудоёмкость, ручные решения экономиста, расчёт, проверку и отчёты.

В ветке astra-harness проекта finance подготовлены общие механизмы ПАИШ: описание способностей, сборка исполнителей под задачу, версии и источники, независимые проверки, управляемое развитие и обмен между подразделениями. Его предметная модель смет и стоимости вычислений не заменяет предметную модель demo-ui.

Цель доработки — применить подходы astra-harness к существующей системе экономического отдела, сохранив её предметный смысл, самостоятельную эксплуатацию и возможность будущего согласованного подключения к ПАИШ.

**Обязательное решение владельца от 11.09.2026: demo-ui утверждён; концепция ПАИШ ещё должна быть одобрена шефом. Автономная работа demo-ui сохраняется независимо от принятия, доступности и изменения общих правил ПАИШ.**

### 1.1. Результат для экономиста

После доработки экономист должен:

- продолжать загружать документы, проверять извлечённые строки, задавать условия в чате, считать и сравнивать планы, просматривать замечания и выгружать результат;
- видеть, на каких данных, правилах и версиях построен расчёт;
- различать исправление конкретных данных и изменение общего поведения агента;
- заказывать новую способность или проверку и получать проверяемый результат её внедрения;
- сохранять доступ к прошлым планам после изменения документов, агентов и подключения либо отключения ПАИШ.

## 2. Состав и границы работ

### 2.1. Обязательная локальная доработка

В состав входят:

1. Уточнение правил разработки и источников требований.
2. Реестр описаний существующих способностей, инструментов, моделей и предметных профилей.
3. Полные версии, снимки контекста и состава расчёта.
4. Область применения исправлений экономиста и история принятия данных.
5. Разделение проверки разработки, аудита результата, локальной приёмки и квалификации способности.
6. Локальный процесс добавления и улучшения способностей с испытаниями, включением и откатом.
7. Учёт недостающей работы и ограниченные повторные попытки.
8. Надёжное локальное исполнение, перенос данных и соответствующие изменения интерфейса.

### 2.2. Необязательная интеграция

В отдельную поставку входят mapping предметных объектов, обмен по выбранной версии протокола, интеграционная identity, доставка сообщений, учёт использования школьных ресурсов и интеграционные испытания.

Проектирование границы адаптера входит в обязательную поставку. Разработка самого адаптера и подключение живой ПАИШ не входят в критерий готовности локальной доработки. Интеграционный пилот выполняется после решения о концепции и утверждения конкретных работ, данных и полномочий.

### 2.3. За пределами ТЗ

Настоящее ТЗ не поручает:

- заменять математическую модель, язык или основные интерфейсы продукта;
- менять суммы, пределы выплат, порядок целей и спорные экономические правила без отдельного предметного решения;
- реализовывать отсутствующую сверку начислений с бухгалтерским фактом только ради полноты каталога;
- заменять оптимизатор языковой моделью;
- переносить всю организацию на школьную авторизацию, PostgreSQL или общий coordinator;
- автоматически передавать ПАИШ документы, ФИО, зарплаты и переписку;
- создавать постоянные процессы для каждой карточки агента;
- запускать бесконечное самоизменение или выполнять реальные платежи.

## 3. Целевая архитектура и термины

```text
Экономист → интерфейс / чат / существующий CLI
                     ↓
        Предметные сервисы demo-ui
        реестр → вход → solver → аудит → отчёт
                     ↓
        Локальный слой исполнения и развития
        версии, решения, проверки, кандидаты, история
                     │
                     └── необязательный адаптер → ПАИШ
```

Предметное ядро не зависит от сетевых сервисов ПАИШ и не импортирует её обязательный runtime. Локальные механизмы реализуются в проекте или поставляются как независимая библиотека без зависимости от школьной инфраструктуры. Общий сетевой адаптер подключается через явный интерфейс.

| Термин | Смысл в этом ТЗ |
| --- | --- |
| Роль | Устойчивая ответственность и название для человека |
| Способность / capability | Обещание получить типизированный результат в конкретной области |
| Процедура / skill | Повторяемый способ работы с входом, выходом и проверками |
| Инструмент / tool | Исполняемый обработчик: парсер, solver, аудит, экспорт и другие |
| Предметный профиль / domain profile | Версии правил, источников, единиц и условий применимости |
| Сессия | Ограниченное выполнение выбранной процедуры в рамках конкретной задачи |
| Квалификация | Подтверждённая пригодность сочетания версий для определённого применения |
| Локальная приёмка | Решение о пригодности конкретного результата в demo-ui |
| План ФОТ | Предметное распределение выплат по сотрудникам, договорам и месяцам |
| План работ ПАИШ | Граф заданий на получение и проверку результата; не план выплат |
| Выпуск | Неизменяемый согласованный набор версий |
| Закрепление версии / pin | Использование точной версии на протяжении данного запуска |
| Контрольный набор / baseline | Зафиксированные исходные данные, версии, ожидаемые свойства и результаты сравнения |

Оптимизатор остаётся детерминированным вычислительным инструментом. Наличие фиксированных предметных обработчиков не противоречит динамическому выбору необходимых процедур. Запрещается требовать исполнения всего каталога ролей на каждом задании.

## 4. Правила оформления и статусы требований

Каждый ID из раздела 5 является отдельным требованием. Источники, владельцы и точки реализации указаны по группам; положительный и отрицательный сценарии — в разделе 10. Эти сведения вместе образуют карточку по [шаблону проекта](ШАБЛОН_ТРЕБОВАНИЯ.md).

Для всех новых технических требований исходный статус — **рабочая гипотеза: предложено настоящим ТЗ**. Условия самостоятельности из U2 подтверждены владельцем. Подтверждённые и спорные экономические требования сохраняют собственные статусы в D1–D3.

Начальное состояние реализации всех новых требований — `not_started`; испытания — `not_run`. Уже имеющееся поведение может быть зачтено как переиспользованное только после проверки и записи evidence.

Общие правила карточек:

- неизвестные источник, полномочие или область не заполняются предположением;
- отсутствие обязательного входа даёт структурированный вопрос/ошибку, отсутствие инструмента — явную недоступность;
- нарушение обязательного применимого требования имеет тяжесть `error`; информационная недоступность необязательной ПАИШ не является ошибкой локального расчёта;
- сообщение проверки содержит ID, объект, версию, период, факт, ожидаемое значение, единицу и источник, когда эти поля применимы;
- любой пробел покрытия записывается явно; «нет случая» не равно «пройдено»;
- решения, изменения и результаты проверок сохраняются с датой и ответственным.

## 5. Функциональные требования

### 5.1. Самостоятельная работа — AUT

Источники: U1, U2, D5. Владелец: владелец продукта. Точки реализации: конфигурация, зависимости пакета, запуск web/CLI, граница адаптера.

**AUT-001. Независимая установка и запуск.** Обычная установка и все ранее поддерживаемые локальные сценарии должны работать без пакетов, адреса, учётной записи, схем, регистрации и разрешения ПАИШ. Режим по умолчанию — `standalone`. Собственные зависимости demo-ui, включая solver и провайдера LLM для соответствующих операций, остаются явными.

**AUT-002. Независимость от состояния и правил ПАИШ.** Недоступность ПАИШ, отсутствие одобрения её концепции и изменение школьных контрактов не должны блокировать локальный расчёт, приёмку, выпуск или развитие способностей. При выключенной интеграции запрещены фоновые сетевые обращения к ПАИШ и ожидание её сервисов.

**AUT-003. Обратимость подключения.** Отключение адаптера сохраняет доступ к реестру, источникам, планам, результатам, локальным решениям и истории. Школьные незавершённые операции сохраняют честный статус; их отключение не выдаётся за исполнение или одобрение школой.

### 5.2. Сохранение предметной модели — DOM

Источники: U1, D1–D5. Владелец: экономический отдел. Точки реализации: предметные модели, сборка входа, solver, отчёт, чат.

**DOM-001. Сохранение пользовательского сценария.** Сохранить общий реестр организации, многолетние документы, отдельные годовые планы, документы песочницы, штатные форматы Excel, ручные фиксации и запреты, действующие действия чата и экспорт. Версионирование не должно требовать повторной загрузки общего документа в каждый план.

**DOM-002. Сохранение экономических правил.** При адаптации harness сохранить правила подтверждённой версии D1–D3, включая направленное замещение, учёт по строке сотрудника, шаг ставки, атрибуцию РКМ, условия П4/БЭП и разрешения видов выплат. Сохранить решения SOURCE-001 и SOURCE-002. Порядок стадий solver не меняется; экономист изменяет только предусмотренные настройки и веса разрешённой стадии.

Спорные остаток ФОТ 1 000 ₽, трёхмесячный блок оклада и трактовка строки совместительства не подтверждаются и не отменяются техническим рефакторингом. Их существующее поведение и статус фиксируются в baseline.

**DOM-003. Различение денежных контуров.** ФОТ, поступления и остатки договоров остаются предметными данными. Использование LLM/CPU/solver учитывается отдельно. Расчёт или сравнение планов не создаёт бухгалтерский факт начисления и не списывает ФОТ как бюджет вычислений.

### 5.3. Каталог и выбор способностей — CAP

Источники: U1, A1, A2. Владелец: владелец продукта; исполнитель: разработчик. Точки реализации: `app/agents.py`, каталог описаний, локальный resolver и обработчики.

**CAP-001. Типизированные описания.** Для каждой используемой способности хранить стабильный ID, версию, владельца, назначение, схемы входа/выхода, область применения, ссылки на процедуры, инструменты и проверки. Для роли отдельно хранить имя, ответственность и связи с процедурами. Каталог валидируется по зарегистрированной локальной схеме.

**CAP-002. Зрелость и доступность.** Различать зрелость `declared / implemented / qualified / suspended` и текущую доступность. `real=True` при миграции не означает `qualified`. `real=False` сохраняется как нереализованная возможность. Недоступный сервер работающего инструмента не превращается автоматически в заявку на разработку нового.

**CAP-003. Минимальный применимый состав.** Выбирать процедуры и проверки по типизированному заданию, данным, предметному профилю, разрешениям и ресурсам. Переименование роли/плана не меняет маршрут. Pure tool выполняется без обязательной LLM. Отсутствие обязательной способности возвращает причину и требуемое действие; экспериментальные версии разрешены только в испытательной области.

**CAP-004. Явная привязка проверки.** Для обязательной проверки хранить правило применимости и связанный requirement ID. Наличие checker в каталоге само по себе не запускает его. Неприменимость должна иметь проверяемое основание; отсутствие реализации не является основанием `not_applicable`.

### 5.4. Версии и воспроизводимость — VER

Источники: U1, D3, A2, A5. Владелец: технический ответственный. Точки реализации: `app/agents.py`, хранилище артефактов, `app/db.py`, сборка входа и запуск.

**VER-001. Полный состав версии.** Сохранять отдельные версии процедуры, инструмента, предметного профиля, модели и набора проверок. Для материальных артефактов использовать полный SHA-256; для выпусков — SemVer. Короткий прежний SHA-1 сохраняется только как legacy-метка. Версия без LLM всё равно включает код инструмента и его зависимости.

**VER-002. Снимок каждого выполнения.** До первого действия закрепить входные версии, набор процедур/инструментов, профиль, модель, правила проверки, разрешения и лимиты. Для LLM сохранить фактически переданный контекст с выбранными Correction и параметрами вызова в защищённом локальном хранилище; секреты не включать. Для solver сохранить фактические байты входа, справочник, настройки, версию solver и параметры. Финальный выход фиксировать после материальных преобразований отчёта.

Если провайдер не сообщает неизменяемую ревизию модели, записать это ограничение; совпадение имени модели не доказывает полную воспроизводимость.

**VER-003. История и влияние изменений.** Версии файла, результата извлечения и принятой записи различаются. Замена источника убирает его из активного представления по правилам продукта, но сохраняет историю. Дата загрузки и дата действия нормы различаются. Изменение существенной зависимости отмечает затронутые результаты `review_required`; независимые результаты не инвалидируются.

**VER-004. Закреплённые запуски и решения.** Уже начатое выполнение сохраняет версии. Изменение данных или выпуска создаёт новый снимок/попытку, а не переписывает старый. Решение о принятии и проверка относятся к конкретному составу входа/выхода; устаревшее решение не применяется к новой версии. Отзыв опасной версии оформляется отдельным событием остановки/пересмотра с сохранением истории.

### 5.5. Исправления, память и источники — MEM

Источники: D2, D3, A2, A5. Владелец: экономический отдел. Точки реализации: `Correction`, `Verdict`, `Proposal`, `app/intake.py`, `app/llm.py`, harness разбора.

**MEM-001. Область действия исправления.** Correction должен иметь источник, версию документа/извлечения, автора, время, тип сущности, назначение, область организации/плана/формы/периода и статус. До подтверждения широкой применимости исправление ограничено своим контекстом. При неизвестной области автоматическое расширение запрещено. Общий реестр организации остаётся допустимой областью при наличии полномочий.

**MEM-002. Отделение факта от общей процедуры.** Принятие строки меняет данные и создаёт запись решения; не выдаёт полномочия менять нормы, проверки или общую способность. Переиспользование подтверждённой трактовки допускается по явной области и входит в снимок контекста. Обобщённое изменение метода проходит GOV. Удалить безусловное правило подсказки «исправления важнее общих правил»; приоритет определяется типом и областью решения.

Более позднее исправление не считается автоматически истиннее прежнего. Конфликт фиксируется с источниками и разрешается уполномоченным пользователем.

**MEM-003. Версионные случаи проверки.** Verdict связывается с точной версией документа, предложенной строкой и контекстом извлечения, а не только с именем файла. Стенд воспроизводит выбранную конфигурацию с теми же разрешёнными hints. Разделять примеры развития/регрессии и независимый набор оценки общей пригодности. Исторические Verdict без надёжной привязки помечаются неполными и не становятся строгим эталоном автоматически.

### 5.6. Проверка, квалификация и приёмка — QA

Источники: D1, D4, A3. Владельцы: экономический отдел — критерии; технический ответственный — исполнение проверок. Точки реализации: `result_audit.py`, `app/rules.py`, harness, `scripts/check.py`.

**QA-001. Полная матрица применимых проверок.** Создать машиночитаемую матрицу подтверждённых предметных требований: источник/версия → вход → solver → независимый аудит → положительный/отрицательный случай → представление замечания. Для каждого конкретного результата заранее определять обязательный набор. Если слой не реализован, указывать пробел; пустой набор не даёт положительного заключения.

Обязательный объём доработки аудита: зарплата и разрешённый дефицит; ставки; разрешённые виды выплат и связи 120/122/124/152/приказа; П2556, индивидуальная и групповая П4, БЭП; касса и сроки; ручные назначения/запреты; направленное замещение и атрибуция РКМ. Точная формула берётся из подтверждённой карточки. Противоречие источников выделяется в отдельный вопрос; непокрытая область не объявляется полностью проверенной.

**QA-002. Отдельные статусы и проверяемые доказательства.** Хранить раздельно состояние исполнения, solver status, evaluation verdict, локальную приёмку, актуальность результата и зрелость способности. Для каждой проверки записывать вход/кандидат, версию метода и эталона, среду, вызов, измерения, единицы/допуски и результат. Приёмка использует полный набор применимых проверок для exact версии. `failed / inconclusive / error / not_run` обязательной проверки не превращаются в `passed`.

LLM-пересказ замечаний остаётся объяснением. Для утверждения независимой проверки требуется независимый от создающего результат обработчик/процесс с доступом к исходным основаниям, а не другое имя того же агента. Для квалификации автора кандидата отделять от защищённого набора эталонов и исполнителя оценки. Школьная подпись/служба не обязательна для локального evidence.

**QA-003. Честный known_red и совместимость baseline.** Сохранить реестр известных дефектов, их причину, дату, владельца и затронутую область. Команда разработки может сообщать `baseline_compatible`, если новых регрессий нет; сами известные случаи сохраняют verdict `failed`. Отдельный режим проверки квалификации/приёмки не допускает обязательный провал по наличию в known_red.

Продолжение уже утверждённого локального сценария допускается по его зафиксированным ограничениям и статусу legacy. Оно не выдаётся за новую полную квалификацию. Введение этой модели не должно внезапно требовать школьного одобрения существующих операций.

**QA-004. Независимое сравнение кандидатов.** До испытания закрепить контрольный набор, бюджет, основную метрику, все защитные условия, критические случаи, методику и пороги. Сравнить baseline и candidate при сопоставимых условиях. Каждый критический случай оценивается отдельно; суммарный score не компенсирует регрессию. При недостаточных данных результат `inconclusive`. Выход автора и использование раскрытых исправлений не считаются независимой валидацией на скрытых данных.

### 5.7. Добавление и развитие способностей — GOV

Источники: U1, A1, A4, A5. Владельцы: локальный владелец способности и ответственный за выпуск. Точки реализации: локальные заявки, хранилище кандидатов, сервис оценки и переключения версий.

**GOV-001. Единый локальный процесс расширения.** Запрос из чата или интерфейса должен проходить: регистрация потребности → анализ reuse → классификация изменения → описание входа/выхода и применимости → фиксированные критерии → изолированный candidate → проверка → локальное решение → включение → наблюдение/откат.

Классификация различает данные, настройку, skill, tool, domain profile, проверку, роль и отсутствующую capability. Новая роль создаётся при отдельной ответственности. До появления полного мастера все шаги могут выполняться через versioned files и локальный CLI/API; результат процесса обязан отображаться в приложении.

**GOV-002. Полномочия и защищённые изменения.** Правила права доступа, нормативные пределы, порядок целей, обязательность проверок, эталоны/метод допуска и внешние действия меняются по явному локальному решению уполномоченного человека, привязанному к версии и области. Модель не назначает себе роль, автора решения, статус `qualified` или разрешение выпуска.

Обычная подтверждённая правка данных и ранее разрешённое действие чата исполняются в существующем рабочем сценарии. Повторное согласование каждого действия не требуется. Обратимое улучшение может включаться автоматически только в заранее утверждённой локальной политике с областью, лимитами и откатом. По умолчанию автоматическое продвижение новых кандидатов выключено.

**GOV-003. Целостный выпуск и откат.** Candidate и release содержат неизменяемые исходники/артефакты, зависимости, результаты проверок и решение. Активный выпуск переключается целиком с проверкой ожидаемой версии и монотонно возрастающего номера переключения. Последовательное переписывание активных файлов недопустимо.

Перезапуск после переключения сверяется по сохранённому operation ID. Старые процессы сохраняют pins. Откат создаёт новое событие активации предыдущего совместимого выпуска; не стирает изменения данных и не обещает отменить внешние эффекты. Несовместимая миграция данных требует отдельного плана восстановления.

**GOV-004. Разные циклы и ограничение повторов.** Разделять исправление конкретного результата, обнаружение недостающих работ текущего плана и улучшение общей способности. Одна причина может связать эти процессы, но не должна создавать повторные одинаковые заказы.

Для каждого эксперимента установить предел времени, стоимости, кандидатов и повторов. Начальные локальные значения: не более одного активного эксперимента улучшения, двух кандидатов в сравнении и двух автоматических попыток по одному наблюдению. Это пределы, а не разрешение расходов; изменяются локальной политикой. Смена run ID не сбрасывает счётчики. Исчерпание лимита оставляет `deferred / unresolved` с причиной. Запуск web-приложения не запускает бесконечный цикл улучшений.

### 5.8. Надёжное исполнение и недостающая работа — RUN

Источники: D2, A2, A4. Владелец: технический ответственный. Точки реализации: локальный сервис задач, БД, запуск обработчиков, журнал событий.

**RUN-001. Атомарные действия и защита от повторов.** Команды изменения состояния имеют operation ID и проверку версии изменяемого объекта. Повтор той же команды возвращает сохранённый результат; тот же ID с другим содержимым даёт конфликт. Одновременные запросы не создают два активных расчёта одного плана. Запись нового состояния, решения/события и задания на дальнейшую работу выполняется согласованно.

**RUN-002. Восстановление после сбоя.** Долгие задания имеют сохраняемые состояния, владельца исполнения и защиту от записи старого исполнителя. Перезапуск не должен помечать расчёт другого живого процесса как прерванный только по состоянию «идёт». Незавершённый внешний эффект сначала сверяется; слепой повтор запрещён. Для pure вычисления допустим повтор с сохранением связи попыток и исходных pins. Требование реализуется локально без school coordinator.

**RUN-003. Учитываемые пробелы.** Для недостающей страницы РКМ, неизвестного источника нормы, отсутствующего обработчика или проверки создавать запись с типом, exact объектом/версией, evidence, областью влияния, ответственным и критерием закрытия. Виды: input, work, capability, evidence, requirement, invalidated assumption.

Создание задачи не закрывает пробел. Закрытие требует фактического результата/проверки либо обоснованного решения об изменении области. Блокируется затронутая окончательная приёмка; корректирующая работа и независимые планы продолжаются. Повтор одного наблюдения добавляет evidence к существующей записи.

### 5.9. Интерфейс и решения пользователя — UI

Источники: D2, D5, A1. Владелец: владелец продукта. Точки реализации: существующие страницы агентов, плана, документов и замечаний.

**UI-001. Наблюдаемость без смены рабочего интерфейса.** Сохранить компактные таблицы и ленту. Добавить в подходящие существующие представления: версию и зрелость способности, доступность, область применения, последний итог проверки, состояние кандидата и возможность посмотреть историю/сравнение. Для расчёта показать использованный состав и актуальность. Полные хеши доступны в технических деталях, но не дублируются во всех таблицах.

Пояснения агента остаются в чате; в рабочих таблицах — данные, короткие статусы, подсказки и переходы. При выключенной интеграции нет обязательных школьных разделов, пустых согласований и предупреждения, мешающего работе.

**UI-002. Решение по конкретной версии.** Для принятия строки, правила или кандидата показывать предмет изменения, источник, область, версию и последствия. После смены зависимых данных устаревшая форма не должна молча применять решение к новой версии. Простые действия экономиста сохраняют существующие кнопки/чат; интерфейс не требует понимания терминов capability, receipt или grant.

### 5.10. Перенос и эксплуатация — MIG, NFR

Источники: U2, D3–D5, A2, A5. Владельцы: технический ответственный и оператор локальной установки.

**MIG-001. Сохранение существующих данных.** Миграция сохраняет документы/версии/байты, строки реестра, планы, настройки, фиксации, прогоны, отчёты, сообщения, вопросы, предложения и решения. Существующие числовые ID не требуется заменять повсеместно: новые стабильные ID и внешние связи добавляются через mapping. Недостающие исторические сведения отмечаются `legacy_unknown`, без выдуманных версий и авторов.

**MIG-002. Безопасное выполнение миграции.** Реализовать dry-run, резервную копию, проверку исходной версии схемы, идемпотентный перенос, отчёт о количестве/связности записей и план возврата. Испытание проводится на копии/синтетических данных. Миграция живой `app/data/` — отдельная операторская операция. Запрещён одновременный старый и новый путь записи одного активного выпуска.

**MIG-003. Отдельная готовность локального продукта.** SQLite остаётся поддерживаемым локальным хранилищем. Самостоятельные web/CLI, резервное копирование и восстановление не требуют школьной БД. Новые локальные таблицы не являются копией авторитетных школьных таблиц. При нехватке готовности новой части существующее локальное поведение сохраняется в явно обозначенном legacy-режиме.

**NFR-001. Производительность и ограничение нагрузки.** Сохранить решения ADR по persistent solver и атрибуции. Для проверки накладных расходов новой обвязки использовать неизменные входы и окружение, без обращений к LLM. Предлагаемый порог приёмки: медиана трёх прогонов после изменения не хуже baseline более чем на `max(1 секунда, 10% baseline)`. Сравнивать одинаковые стадии и настройки; порог фиксируется до реализации в L0. Исключение требует измерений и решения владельца, а не ослабления проверок.

**NFR-002. Локальные данные и секреты.** Контекст, источники и история защищаются по локальной области доступа. Решения связываются с реальным локальным оператором; строка «экономист» от LLM/клиента не создаёт identity. Для однопользовательской установки допустим идентифицированный локальный оператор и loopback-режим без школьного LDAP; многопользовательский доступ требует локальной аутентификации и проверки полномочий. Полноценная новая система корпоративных учётных записей не входит в ТЗ.

Секреты не включаются в prompts, manifests, отчёты и Git. Профиль модели содержит разрешённую политику обработки данных; добавление fallback не разрешает отправку документов другому провайдеру. Перенос исправлений между организациями/проектами требует явной применимости и прав.

### 5.11. Документация и необязательный обмен — DOC, INT

**DOC-001. Приоритет и область правил.** Обновить AGENTS и индекс документации: различать утверждённое предметное правило, предлагаемую доработку, локальный порядок развития и проект интеграции. Согласовать обзор README с каноническими правилами, включая направленное замещение. Источники: U1, U2, D1–D5; владелец: владелец продукта.

**DOC-002. Продолжение разработки по фактам.** Вести checkpoint с ID пакета/требования, файлами, точными командами, результатами, ссылками на evidence, пробелами и следующим шагом. Инструкции разработчика, runtime-процедуры и требования продукта различаются. Подготовка документов или fixtures не закрывает реализацию. Источники: U1, A1–A5; владелец: технический ответственный.

Следующие требования применяются только к отдельной интеграционной поставке:

**INT-001. Необязательный versioned adapter.** Адаптер переводит локальные объекты в согласованные предметные схемы и общий транспорт выбранной версии ПАИШ. Не добавлять локальные значения в общие enum, не переопределять смысл существующих capability ID. Несовместимость протокола выдаёт явную ошибку обмена. Общий runtime при необходимости является зависимостью адаптера, не основного продукта.

**INT-002. Владение и доступ.** Реестр организации и план ФОТ остаются предметными объектами demo-ui. Школа владеет своими заданиями, grants и школьной приёмкой. Один объект/состояние имеет одного авторитетного writer; mapping связывает их. Локальное принятие результата не становится школьным автоматически. Передавать только разрешённые данные и ссылки, с проверкой identity, project scope, назначения и классификации.

**INT-003. Доставка и отключение.** Для внешних операций использовать durable outbox/inbox, idempotency, проверку версий, lease/fencing и сверку неизвестного эффекта согласно выбранному протоколу. При недоступности ПАИШ связанные операции ожидают восстановления, локальные работы продолжаются. Выключение адаптера не теряет intent/outcome и не повторяет совершённое действие. До реального подключения проверить границы AUT и MIG.

Источники INT: U2, A2–A5. Владелец: согласованный ответственный интеграции; включение — по решению шефа о концепции и scope.

| SkillVersion | ID/версия, назначение, предусловия, типизированный вход/выход, instruction ref, tools, разрешения, область, evaluation suite, поддержанные model profiles |

| DomainProfileVersion | ID/версия, организация/назначение/период, единицы, карточки правил и источники, применимые checks, спорные правила и исключённые области, digest |
| ModelProfileVersion | ID/версия, endpoint alias, модель/доступная ревизия, параметры генерации, схема ответа, ограничения контекста, политика данных, квалификация |
| SourceVersion | Стабильный ID источника, версия файла, hash байтов, тип/имя, locator, uploaded_at, effective_from/to, lineage, область доступа |
| ExtractionSnapshot | Source refs, состав извлечения, точный context ref, предложенные строки, evidence по ячейке/странице, ошибки и limitations |
| RegistryRevision | Сущность и стабильный ID, предыдущая версия, нормализованные значения, источник/извлечение, решение, период действия, статус |
| ContextSnapshot | Разрешённые входы/правила/исправления, материал фактического запроса, версии процедур/модели, digest, политика хранения |
| RunManifest | Run/attempt ID, локальный план и его ревизия, входные артефакты и hashes, composition/context refs, настройки, code/environment/tool refs, ограничения, обязательные checks, выходные refs |
| EvaluationRecord | Check ID, requirement refs, exact candidate/input/plan refs, evaluator/benchmark версии, исполнитель, команда, среда, измерения/допуски, verdict, время, evidence refs |
| LocalDecision | ID, реальный actor и полномочие, вид решения, exact subject refs/digest, область, действие, время, основания |
| Finding | ID, тип пробела, субъект/версия, evidence, последствия, область блокировки, owner, состояние, closure criteria, связанные задачи/решения |
| ImprovementRequest | Потребность, примеры, источник/finding refs, область, reuse diagnosis, вид изменения, owner, ограничения |
| ExperimentPlan | Baseline/candidate refs, development/acceptance sets, primary metric, guardrails, critical cases, пороги, бюджет, повторы и stop conditions |
| ReleaseBundle / Activation | Target ID, source/build/dependency refs, candidate, проверки/решение, compatibility, rollback ref; для activation — operation ID, expected/current generation, outcome |
| IntegrationMapping | Только при подключении: local/external IDs, schema versions, owner каждого состояния, exported digest, статус передачи, operation refs |

Материальные версии immutable. Изменяемые состояния имеют `row_version >= 1`; конкурентная запись проверяет ожидаемую версию. Время служебных событий сохраняется в UTC; бизнес-календарь и месяц расчёта определяются предметным профилем.

Hash байтов файла отличается от hash нормализованного JSON. Для нового канонического JSON выбрать и закрепить реализацию RFC 8785/JCS либо явно версионированный локальный формат с проверяемым преобразованием на интеграционной границе. Старый JSON `sort_keys` не объявлять JCS без конвертации. NaN/Infinity и неоднозначные единицы на контрактной границе отклонять.

Денежные значения обмена/хранения, где требуется точная десятичная семантика, — Decimal или decimal string с валютой и правилом округления. Для solver допускаются численные значения его API с явным преобразованием и проверкой допусков.

### 6.2. Связи происхождения

Обязательная цепочка:

```text
Источник и его версия
    → извлечение и выбранный контекст
    → решение экономиста
    → версия записи реестра
    → снимок входа расчёта
    → результат
    → проверки
    → локальное решение о применении
```

Изменение общей процедуры дополнительно связывает наблюдение, candidate, experiment plan, отчёт и выпуск. Для старых данных допускается неполная цепочка с явно указанными неизвестными звеньями; недостающие сведения не восстанавливаются догадкой.

### 6.3. Локальные операции и совместимость API

Сохранить существующие пользовательские маршруты и CLI либо предоставить обратимо совместимые адаптеры. Новые операции должны проходить единый локальный service layer:

- зарегистрировать и разрешить version ref;
- собрать снимок входа/контекста;
- предложить и применить предметное изменение;
- начать/продолжить/отменить запуск;
- записать проверку и локальное решение;
- зарегистрировать пробел и проверить его закрытие;
- создать candidate, запустить испытание, активировать и откатить выпуск.

Схемы аргументов проверяются до действия. ID обработчика выбирается из установленного доверенного каталога; модель не передаёт исполняемый import/exec или SQL. Мутации используют operation ID, version precondition и проверку области. Сохранённый повтор идентичной операции возвращает прежний результат; новые данные с тем же ключом отклоняются.

Новые локальные сервисы не обязаны повторять школьные URL и DTO. Адаптер обеспечивает отображение на утверждённый внешний протокол; неизвестные серверные поля и состояния не «достраиваются» моделью.

### 6.4. Состояния и переходы

Локальные коды состояний документируются и валидируются отдельно от названий в UI.
Существующие значения `Run.status` сохраняются через совместимое отображение;
solver status не используется как общий автомат исполнения.

| Объект | Основные переходы | Условие перехода |
| --- | --- | --- |
| Исполнение | queued → validating → running → evaluating → result_ready | Проверены вход, версии, права; получены выход и результаты требуемых проверок. result_ready означает готовность пакета к решению, не его принятие |
| Ожидание | validating/running → waiting_human или waiting_dependency → validating | Получен нужный вход/решение/ресурс; повторно проверены закреплённые зависимости |
| Ошибка и отмена | Незавершённое исполнение → failed либо cancel_requested → cancelled | Причина записана; внешний эффект при неопределённости сначала получает unknown_effect и проходит сверку |
| Повтор после отказа | failed → новая связанная attempt | Старая попытка остаётся терминальной; сохранены счётчики общего лимита |
| Локальная приёмка | pending → accepted или rejected; принятое решение для заменённого результата → superseded | Exact evidence и решение доступны, обязательные проверки пройдены для accepted; история прежнего решения сохраняется |
| Актуальность | current → review_required | Изменилась материальная зависимость; старый факт принятия не переписывается, новое применение требует пересмотра |
| Finding | proposed → triaged → planned → verifying → closed | Закрытие только по критерию и evidence; задача сама по себе не даёт closed |
| Отклонение finding | proposed/triaged → dismissed; заменённый scope → superseded | Сохранены основание, полномочие и ссылка на преемника при его наличии |
| Запрос улучшения | recorded → triaged → candidate_ready → evaluating → ready_for_activation | Реализованы обязательства GOV и QA; дополнительно допустимы rejected, deferred и needs_input с причиной |
| Эксперимент | queued → running → evaluating → passed/failed/inconclusive | Вердикт вычисляется по зафиксированным критериям; только passed может быть основанием выпуска |
| Активация | prepared → waiting_decision либо activating → active | Есть требуемое решение/ранее выданная политика, exact bundle и ожидаемая generation |
| Откат | active → rolling_back → rolled_back | Проверена текущая generation, восстановлен совместимый bundle, сохранены данные и история |

Для каждого handler реализовать запрет недопустимых переходов и проверку
ожидаемой версии. Автор результата или LLM не может установить terminal success через
переданное поле статуса. При неизвестном эффекте операции запись остаётся
неопределённой до сверки, а не автоматически становится active/closed.

Workflow запроса улучшения и maturity способности — разные состояния:
`draft/trial/ready_for_activation` не добавляются в enum зрелости. Присвоение
qualified требует QA; активация требует GOV. Результат эксперимента passed
сам по себе не переключает активную версию.

## 7. Перенос существующих агентов

Сохранить пользовательские названия и прежние ссылки там, где они уже используются. Новые технические ID ниже — предлагаемый локальный каталог; внешняя публикация в ПАИШ отдельно согласуется.

| Текущий ключ | Целевая ответственность | Начальное действие |
| --- | --- | --- |
| intake | Извлечение предложений и сборка предметных входов | Разделить процедуры известных форм и LLM-разбора; описать источники и критерии |
| tuning | Преобразование разрешённых пожеланий в настройки | Оформить типизированный результат изменения и существующие детерминированные ограничения |
| solver | Расчёт плана ФОТ | Зарегистрировать ToolVersion; не превращать в LLM-персону |
| infeasible | Диагностика отсутствия решения | Привязать вывод к фактическим проверкам/опытам и их стоимости |
| scenario | Сравнение планов | Закрепить общий baseline и раздельные альтернативы |
| norms | Проверка новой редакции нормативов | Разделить извлечение различий и решение о применении нормы |
| checker | Объяснение замечаний | Отделить от независимого числового аудита; существующее имя можно сохранить |
| memo | Материалы по результатам | Использовать только закреплённые данные и допустимые источники |
| reconcile | Сверка плана с фактом начислений | Оставить declared/нереализованным, если фактический обработчик не найден |

Для каждого обработчика в L0 составить запись: существует ли реализация, какие входы реально поддерживает, какие проверки есть, ограничения, зависимости от модели и текущее использование. Не считать текст `does` доказательством работоспособности.

Заявки «добавить агента» проверяют этот каталог до создания новой роли. Проверка, необходимая для результата, добавляется как обязательство с применимостью даже при отсутствии новой пользовательской карточки.

## 8. Испытание улучшений и решения

### 8.1. Протокол сравнения

До создания отчёта по candidate зафиксировать:

| Поле | Требование |
| --- | --- |
| Гипотеза | Конкретная причина дефекта и ожидаемый эффект изменения |
| Область | Виды документов/задач, организация, период, модель/инструмент |
| Baseline | Точная версия действующего поведения и данных |
| Наборы | Открытые примеры, регрессия, независимая оценка и критические случаи; права на данные |
| Основная метрика | Одна заранее выбранная измеримая величина с единицей и порогом |
| Ограничения | Полнота, ложное принятие, ложные замечания, источники, права, стоимость, время |
| Правило критических случаев | Каждый обязательный случай проходит отдельно |
| Методика | Парное сравнение, количество запусков/seed при применимости, трактовка нестабильности |
| Остановка | Лимиты, причина inconclusive, условие передачи человеку |
| Выпуск | Кому и для каких новых задач можно включить; условия отката |

Для извлечения измерять пропущенные и лишние сущности, точность полей и происхождения, долю необходимых исправлений. Для аудита — найденные реальные нарушения и ложные замечания. Для solver — предметные инварианты, значения стадий и длительность. Количество агентов, замечаний или правок не является метрикой успеха.

### 8.2. Решения и квалификация

Одобрение данных, одобрение трактовки нормы, разрешение экспериментального применения и разрешение выпуска — разные виды LocalDecision.

Квалификация относится к tuple «skill/tool/model/profile/назначение/область», а не ко всем действиям роли. Обновление значимой зависимости требует оценки влияния и повторных проверок затронутой области. Успешное переименование не требует повторного solver-расчёта.

Для локальной приёмки механизма достаточно воспроизводимого полного цикла на одной реально исполняемой детерминированной процедуре или проверке и отдельного отрицательного кандидата. Испытания на fake LLM подтверждают протокол обработки ответа, а не качество живой модели. Остальные способности получают только фактически подтверждённый статус. Недоступный провайдер не мешает эксплуатации сохранённой автономной части, но не позволяет объявлять этот профиль qualified.

### 9.2. Миграционная последовательность

1. Сделать опись структуры и подготовить изолированную копию данных.
2. Выполнить dry-run, проверить свободное место и возможность восстановления.
3. Добавить новые таблицы/поля и readers без удаления старых данных.
4. Сохранить legacy IDs/hashes, построить только доказуемые связи происхождения.
5. Перенести описания обработчиков и зафиксировать исходный локальный выпуск.
6. Проверить чтение прошлых планов/отчётов и отсутствие записи в исходную копию.
7. Переключить новый локальный writer; исключить второй путь изменения того же active target.
8. Повторно запустить миграцию: новых дубликатов быть не должно.
9. Проверить восстановление на копии и оформить операторскую инструкцию.

Не запускать автоматическую миграцию живых данных ради импорта модуля в тесте. Для существующих импортирующих стендов сохранить `FOT_SKIP_ORPHANS=1` до устранения стартовых побочных эффектов.

## 10. Приёмочные испытания

Все сценарии ниже имеют исходный статус `not_run`. Для каждого разработчик реализует отдельные положительные и отрицательные случаи; общий ID таблицы получает суффиксы `-P` и `-N`. Дополнительные подслучаи нумеруются. Ссылки на реальные test IDs и результаты вносятся в матрицу покрытия.

Тесты не должны изменять живую базу, использовать секреты автора или обращаться к ПАИШ в локальном профиле.

### 10.1. Обязательные экономические подслучаи

В рамках T-DOM-002 и T-QA-001/002 обеспечить отдельные случаи:

- RATE-001: допустимы 0; 0,25; 0,75; 1,5 и численная погрешность около допустимого значения; недопустимы 0,3; 0,86; отрицательная ставка.
- Выплаты: полная зарплата без разрешённого дефицита и честно отмеченный дефицит при разрешении; скрытая недоплата недопустима.
- П4: индивидуальное равенство при активированной 124 и отдельное групповое ограничение; замена обоих одним потолком не проходит.
- П2556/БЭП: проверка в единицах, по объектам и периоду, установленным карточками; усреднение по неподходящей совокупности не проходит.
- 120/122/152/приказ: соответствие разрешённым источникам и связям; приказ не создаёт трудоёмкость.
- Замещение: допустимое направленное отношение и недопустимое обратное.
- РКМ: однозначная атрибуция сотрудник–договор–месяц; попытка дробления между двумя строками отклоняется; годовая строка и строка по месяцам проверяются раздельно.
- Касса/сроки: перенос остатка вперёд и выплаты в своём окне; расход до поступления и после разрешённого срока не проходят.
- Ручные назначения: допустимая фиксация соблюдается; противоречащая подтверждённым ограничениям не обходится автоматически.
- Источники: отсутствие крайнего срока использует конец договора; явное разрешение 124 соблюдается независимо от типа договора согласно SOURCE-002.

Для каждого числового случая зафиксировать единицы, точность, исходник и ожидаемое поведение по действующей карточке. Если канонические документы противоречат друг другу, сначала создать карточку открытого решения, не подгонять ожидаемый результат по одному текущему запуску.

### 10.2. Профили и команды проверки

Сохранить действующие команды:

```text
python scripts/check.py --changed
python scripts/check.py --quick
python scripts/check.py
python scripts/check.py --full
```

При реализации добавить профили/команды с документированным эквивалентом:

| Профиль | Что проверяет | Зависимость от внешней среды |
| --- | --- | --- |
| local-contract | Схемы, версии, полномочия, повторы и states на временной БД | Без ПАИШ и внешней модели |
| local-regression | Предметные случаи, чат, аудит, UI-логику | Локальный solver; ответы LLM подставлены |
| local-e2e | Известные формы → реестр → расчёт → аудит → Excel; перенос и история | Собственные локальные зависимости demo-ui |
| capability-evaluation | Сравнение конкретного baseline/candidate по ExperimentPlan | Только заявленные разрешённые модели/инструменты/данные |
| paish-contract | Обмен и отказы на fake hub | Только I1; живая ПАИШ не нужна |
| paish-live | Реальный согласованный обмен и права | Только I2 |

CLI-имена новых профилей выбираются в L0 и фиксируются до их реализации. Это описание требуемых проверок, не утверждение о наличии этих команд сейчас.

Машинный отчёт содержит: ID проверки/требования, фактический verdict, источник evidence (`live / replay / synthetic / analytical` при применимости), версии, команду, exit code, измерения, known-defect ref и summary. `baseline_compatible` относится к сводке разработки, не к verdict отдельного check.

Отсутствующая обязательная зависимость проверки обозначается `not_run/error` и делает соответствующий профиль непрошедшим; неиспользуемая интеграция не включается в required set локальной поставки.

Существующий отключённый pytest не считать приёмкой. Новые тесты должны реально запускаться отдельными входами harness/команды проверки и входить в CI. Восстановление старого набора pytest допускается по совпадающим требованиям, но не является обязательной переписью всех прежних тестов.

## 11. Комплект поставки и готовность

### 11.1. Обязательная локальная поставка

Исполнитель передаёт:

1. Код доработки с сохранёнными web/CLI и локальной установкой.
2. Миграции, dry-run, отчёт переноса и проверенную инструкцию восстановления.
3. Схемы, исходные manifests существующих обработчиков и локальный release.
4. Матрицу требований/проверок и раздельные статусы capabilities.
5. Реально исполняемые положительные/отрицательные тесты и отчёты.
6. Сквозную демонстрацию локального цикла развития: потребность → reuse → candidate → сравнение → решение → включение → откат; один успешный и один отвергнутый кандидат.
7. Обновлённые канонические документы, инструкции добавления способности и checkpoint.
8. Перечень оставшихся предметных споров, ограничений квалификации и неподтверждённых областей.

Локальная поставка принимается, когда L0–L5 завершены, обязательные новые проверки пройдены, сохранение baseline доказано, история не утрачена и AUT выполняется. Существующие известные дефекты допускаются только как явно учтённый исходный долг; новый обязательный дефект не переносится в known_red ради завершения пакета.

Наличие технического механизма квалификации не означает, что все исторические роли уже qualified. Такой статус присваивается только по фактической проверке заявленной области. Для каждой способности в поставке должно быть понятно: что реализовано, что проверено, для чего допущено и какие ограничения остаются.

### 11.2. Необязательная поставка интеграции

Отдельно передаются адаптер, зафиксированные версии протокола, mapping, contract tests и инструкция включения/отключения. Реальное подключение подтверждается отдельным отчётом I2. Отсутствие этой поставки не является незавершённостью локального ТЗ.

### 11.3. Запрещённые способы формального закрытия

Нельзя закрывать требование:

- наличием карточки агента без исполнения нужной процедуры;
- успешным статусом solver вместо предметной проверки;
- подписью или текстом модели вместо фактического evidence;
- отсутствием найденных ошибок при неполном наборе checks;
- признанием synthetic/fake эксперимента доказательством качества живой модели;
- ослаблением правила или переносом нового дефекта в known_red;
- объявлением старого результата новым qualified после миграции;
- ожиданием одобрения ПАИШ как причиной не завершать независимую локальную работу.

## 12. Порядок работы исполнителя

1. Прочитать AGENTS, индекс документов, это ТЗ и канонические документы изменяемой области.
2. Проверить HEAD, рабочее дерево и изменения после исходного commit; сохранить пользовательские правки.
3. Начать L0, зафиксировать текущие тесты и реальные точки исполнения.
4. Работать одним проверяемым пакетом или его ограниченной частью; сначала карточки/критерии, затем код.
5. Для каждого изменения выполнить положительные и отрицательные проверки на изолированных данных; UI проверить на трёх ширинах при его изменении.
6. Записать фактические результаты в checkpoint; не подменять журнал самоотчётом.
7. При предметном противоречии сохранить отдельный вопрос и продолжать независимую работу.
8. Не запускать интеграционный пилот, новые внешние передачи и миграцию живой базы без соответствующего поручения. Подготовка настоящего ТЗ их не разрешает.
9. Завершить отчётом: что изменилось, что проверено, ограничения, безопасный откат и следующий незавершённый пакет.

Форма записи checkpoint:

```text
Дата / исполнитель:
Пакет / часть / requirement IDs:
Исходный commit / состояние дерева:
Что переиспользовано:
Файлы и версии:
Команды / среда / exit codes:
Положительные случаи:
Отрицательные случаи:
Evidence refs / hashes:
Миграция / restart / rollback:
Непройденное / not_run / known debt:
Открытое предметное решение и ответственный:
Следующий конкретный шаг:
```

## 13. Решения, оставляемые предметному владельцу

Следующие вопросы не отменяют самостоятельную реализацию технического слоя:

| Вопрос | Правило до решения |
| --- | --- |
| Остаток ФОТ «0 либо не меньше 1 000 ₽» | Сохранить legacy-поведение и статус спора; не объявлять новым подтверждённым нормативом |
| Минимальный трёхмесячный блок оклада | Сохранить отдельно от подтверждённых требований до уточнения источника |
| Допустимая роль строки совместительства | Не изменять семантику техническим рефакторингом |
| Конкретные лица для утверждения норм, квалификации и выпуска | Использовать настраиваемые локальные обязанности; не создавать фиктивных людей |
| Допуск новых типов документов/моделей | Квалифицировать в указанной области; отсутствие данных не заменять универсальным допуском |
| Утверждение концепции и scope ПАИШ | Интеграция выключена; локальные L0–L5 выполняются независимо |
