# Проверка качества и harness

Цель обвязки — не заставить одну модель критиковать собственный ответ, а
проверять результат независимыми слоями. Чем точнее правило можно выразить
кодом, тем меньше оно зависит от формулировки LLM.

## Слои проверки

### DEV-GUARD-001 · изменения не теряют регрессионную защиту

Статус: подтверждено пользователем, 11.09.2026 («доработай» защиту от потери
требований и ослабления тестов). Источник требования — текущая задача.

- Ошибка или изменение поведения регистрируется в `harness/changes.json`:
  ID, ожидаемое поведение, ссылка на каноническую карточку, затронутые файлы,
  регрессионные тесты и состояние работы. Это очередь изменений, а не вторая
  карта требований; карта Фейбла `docs/requirements-map.json` сохраняет свою роль.
- Изменённый продуктовый код (`app/`, `src/`, исполняемый `docs/ui/`) требует
  обновлённой записи, обновлённой карточки и нового/изменённого теста.
  Зарегистрированный тест должен существовать и входить в запускаемый стенд.
- Изменение/удаление существующих тестов, канонических правил, самой защиты,
  настроек hooks/CI или known_red показывается как `review_required` с diff
  относительно базового commit. Это запрос ревью, не автоматический вывод
  об ухудшении. Новый тест в новом файле не считается ослаблением старого.
- Поле «одобрено» в JSON не снимает review_required. Независимое подтверждение
  и обязательный запрет слияния требуют настройки защиты ветки на GitHub.
- Кеш Stop действителен только для того же содержимого файлов и набора
  команд. Изменение во время проверки не сохраняется как успешная проверка
  нового состояния. Ошибка чтения состояния Git не даёт использовать кеш.

Проверка: `scripts/change_guard.py`, регрессии `scripts/test_change_guard.py`.
Допустимо: запись + карточка + новый тест к исправлению. Недопустимо: изменение
кода без записи, ссылка на отсутствующий тест, удалённый старый тест, повторное
использование успеха после новой правки. Конфликт оставляет запись незакрытой.
Граница: статический контроль не доказывает, что тест достаточно сильный;
сначала нужно показать его падение на старом поведении, затем успешный прогон.
Полная семантическая совместимость всех требований автоматически не доказуема.

1. **Валидация входа** отклоняет отсутствующие, конфликтующие и неверно
   типизированные данные до решателя.
2. **Модель решателя** строит план только в пределах записанных ограничений.
3. **Аудит результата** читает готовые числа независимо от статуса решателя и
   применяет карточки правил из `docs/ПРАВИЛА_РЕШАТЕЛЯ.md`.
4. **Harness** подаёт малые положительные и отрицательные примеры и проверяет
   ожидаемый итог.
5. **LLM-ревьюер** объясняет уже найденные замечания экономисту. Он полезен для
   приоритизации, но не заменяет числовую проверку.

Статусы решателя и аудита разделены: `OPTIMAL` означает, что решена записанная
математическая модель; `audit_status = FAIL` означает, что готовый план не
соответствует внешнему правилу.

## Что реализовано сейчас

| Контур | Файл | Назначение |
| --- | --- | --- |
| хуки правок | `scripts/lint_changed.py`, `scripts/test_lint_changed.py` | синтаксис после прямой правки и команд оболочки |
| карта требований | `docs/requirements-map.json`, `scripts/check_requirements_map.py` | пути, номера случаев, полнота ID ТЗ, совпадение с каталогом агентов |
| разбор документов | `harness/run.py`, `harness/cases.py` | документ → реестр и сверка извлечённых строк |
| чат | `harness/chat.py` | реплика → безопасное действие сервиса |
| жизненный цикл прогонов | `harness/lifecycle.py` | владелец и heartbeat прогона, ключ операции запуска (RUN-001/002) |
| кризис-сценарии | `harness/crisis.py` | малые случаи правил решателя |
| аудит готового плана | `src/fot_planner/result_audit.py`, `harness/audit.py` | независимые проверки результата |
| демо без сервиса | `scripts/demo_offline.py` | сквозной расчёт набора из `data/demo/` |
| демо через API | `scripts/demo_run.py` | приложение, расчёт и отчёт |
| список замечаний | `app/static/issues.js`, `scripts/test-issues.cjs` | контракт замечания и переход к строке отчёта |
| единая приёмка | `scripts/check.py` | запуск контуров и общий код возврата |

Независимый аудит результата содержит карточки `SALARY-001`, `PAYMENT-001`,
`LABOR-001`, `PERSON-001`, `FOT-001` и `RATE-001`. Они проверяют готовый план
по зарплате, доступности выплат, трудоёмкости, личным лимитам, деньгам и шагу
ставки. Остальные ограничения должны добавляться в эту же матрицу вместе со
случаем стенда.

В приложении есть агент № 8 «Проверка результата». Функция
`app/main.py::_review_result` передаёт DeepSeek предупреждения и полный пакет
состояний числовых проверок. Агент ищет межправиловые противоречия и подозрительные
числа, но не меняет план и не подменяет детерминированные проверки.

## Команды

### FOT-HARNESS-TZ-001/QA-003 — честный итог существующей приёмки

Статус требования: рабочая гипотеза ТЗ, взята в реализацию по поручению
пользователя продолжить работу. Область этой части — существующий CLI и Stop,
не полная квалификация способностей и не изменение экономических норм.

Критерии: успешный непустой прогон — `passed`; известный провал решателя
остаётся `failed`, а только разработческий итог может быть
`baseline_compatible`. В `--strict` такой прогон возвращает ненулевой код.
Ошибка запуска, неполный протокол, противоречие между итогом и кодом возврата
не могут быть списаны на known_red. Номер известного случая относится только
к `harness/crisis.py`, не к одноимённым случаям других стендов.
Пустая выборка — `not_run`, в строгом режиме это не успех.

Положительный пример: два напечатанных успешных случая, соответствующий итог,
код 0. Отрицательные: известный провал с кодом 1 в строгом режиме; авария после
такого провала; чужой стенд с тем же номером; отсутствующий исполнитель.
Исполнение и независимые регрессии: `scripts/check_results.py`,
`scripts/test_check_results.py`; подключение через `scripts/parts.py`.
JSON-отчёт фиксирует фактическую область запуска, команды, коды, длительности,
результаты и SHA-256 вывода без помещения самого вывода в отчёт.
Пробел: полнота обязательного набора требований QA-001 и весь формат
qualification evidence QA-002 ещё не реализованы; `--strict --quick` их
не подменяет и не проверяет живую LLM.

```bash
.venv/Scripts/python.exe scripts/check.py --changed
.venv/Scripts/python.exe scripts/check.py --quick
.venv/Scripts/python.exe scripts/check.py --quick --strict --report outputs/check.json
.venv/Scripts/python.exe scripts/check.py
.venv/Scripts/python.exe scripts/check.py --full
```

Отдельные контуры:

```bash
.venv/Scripts/python.exe harness/chat.py
.venv/Scripts/python.exe harness/audit.py
.venv/Scripts/python.exe harness/crisis.py
node scripts/test-issues.cjs
```

`--quick` не обращается к модели. Обычный запуск добавляет разбор документов,
а `--full` — сквозной демо-счёт.

`--strict` применяется к выбранным частям и не прощает known_red; этот режим
включён в CI. `--report` сохраняет JSON даже при провале проверок или пустой
выборке. Отчёт содержит только измеренные факты: hash точки входа — не hash
всех зависимостей, hash вывода вычисляется после декодирования в UTF-8.
Сам вывод остаётся в терминале, не копируется в JSON. Ошибка сохранения
запрошенного отчёта возвращает ненулевой код. Старый отчёт при неудачной
записи может остаться на диске: проверяйте exit code и run_id, не только файл.
Stop остаётся разработческими воротами с прежним десятиминутным кешем,
а не строгой квалификацией каждого снимка кода.

Проверка списка замечаний на Node входит в `--changed`, `--quick` и CI. Без
установленного Node эта часть считается непрошедшей, а не пропущенной: до
11.09.2026 тест жил вне приёмки и сутки падал незаметно.

Скрипт, который импортирует `app/main.py`, обязан до импорта установить
`FOT_SKIP_ORPHANS=1`. Иначе стартовый код приложения может принять живой
расчёт другого процесса за осиротевший и пометить его прерванным. Штатные
скрипты `check.py` и harness уже устанавливают этот флаг.

Хук `scripts/lint_changed.py` сразу проверяет синтаксис после `Edit`/`Write`,
а после успешного или неуспешного `Bash`/`PowerShell` проверяет все изменённые
в Git файлы Python, JavaScript и JSON. Поэтому правка, сделанная запущенным из
оболочки скриптом, не ждёт финальных ворот `Stop`, чтобы стать видимой агенту.

Строки, которые модель извлекла из документа незнакомой формы, являются
предложениями и не попадают в реестр без подтверждения экономиста. Это особенно
важно для правдоподобных, но неверных данных ГОЗ. Правило не относится к
известным формам с отдельным детерминированным обработчиком.

## Как добавить требование

1. Создать или дополнить карточку с ID, источником, статусом и примерами.
2. Решить, где правило должно исполняться: на входе, в решателе или после него.
3. Если нарушение видно в готовом плане, добавить независимую функцию аудита.
4. Добавить минимум один допустимый и один недопустимый случай.
5. Связать ID в документе, проверке и harness.
6. Запустить затронутый контур и общую быструю приёмку.
7. Если слоя пока нет, записать пробел покрытия рядом с правилом.

Для большого списка требований сначала составляется матрица:

| ID | Источник | Вход | Решатель | Аудит результата | Положительный случай | Отрицательный случай | Статус |
| --- | --- | --- | --- | --- | --- | --- | --- |
| RATE-001 | слова экономиста | — | да | да | а01, а05 | а02–а04, а06 | подтверждено; а07 отдельно проверяет пустой план |

Наличие строки без отрицательного случая не считается полным покрытием.

## Известное красное

`harness/known_red.txt` содержит только разобранные случаи, которые ждут
решения человека. Они остаются `failed`; только разработческий режим допускает
`baseline_compatible` с кодом 0. Строгий режим и CI возвращают ненулевой код.
Сейчас список пуст: случаи 09 и 26 получили явные ожидаемые
исходы после фиксации допуска трудоёмкости и ограничения ФОТ/договоров. После
решения запись удаляется вместе с исправлением и тестом.

## Состояние pytest

`tests/` временно отключены через `tests/conftest.py`: прежний контракт тестов
разошёлся с текущим решателем. `pytest` специально не должен выглядеть зелёной
приёмкой при отсутствии выполненных тестов. До восстановления этого набора
источником результата служит `scripts/check.py`.
