# ADR: один persistent-решатель для лексикографических стадий

- Статус: принято и реализовано
- Дата: 2026-09-11
- Код: `src/fot_planner/optimizer.py::_run_solver`

## Контекст

Решатель минимизирует цели последовательно: результат более важной стадии
фиксируется ограничением, затем меняется целевая функция. Создание нового
экземпляра HiGHS на каждой стадии заново переводило неизменную Pyomo-модель и
делало даже малый демо-набор неприемлемо медленным. Отдельные нулевые стадии
тоже тратили время на доказательство уже очевидной нижней границы.

## Решение

Один Appsi/HiGHS solver сохраняется на модели и используется всеми стадиями.
Между вызовами передаются новая цель и добавленные фиксации, сохраняется тёплый
старт. Если неотрицательная цель уже равна нулю на текущем решении, новый запуск
решателя пропускается и ноль сразу фиксируется.

Для целочисленной стадии количества договоров используется нулевой MIP gap.
Для денежных стадий фиксация учитывает численную погрешность; если следующая
стадия неожиданно становится неразрешимой, последняя фиксация ограниченно
ослабляется и повторяется.

Лимит времени передаётся прямо аргументом `timelimit` в `solver.solve()`.
Pyomo/Appsi перед вызовом заменяет ранее установленный `config.time_limit`
значением собственного аргумента, которое без явной передачи равно `None`.

Ключи человеко-месяцев создаются только для строк, где в рассматриваемом
месяце существует хотя бы один разрешённый вид выплаты. Для остальных строк
сразу задаётся нулевой результат. На контрольном демо-наборе эта фильтрация
сократила прогон с 528 с (`FEASIBLE`) до 102 с (`OPTIMAL`).

Нулевой gap описывает способ доказать оптимальность целочисленной стадии, а не
подтверждает деловое правило о числе договоров с остатком ФОТ. Статус этого
правила ведётся отдельно в `docs/CONTRACT_REMAINDERS.md` и `ИСТОЧНИКИ.md`.

## Последствия

- порядок и смысл стадий сохраняются;
- повторный перевод всей модели между стадиями исключён;
- производительность зависит от корректной настройки обновлений Appsi;
- изменение состава переменных или ограничений между стадиями требует
  пересмотреть настройки persistent solver и добавить регрессионный замер;
- удаление передачи `timelimit` аргументом или отбора ключей `labor_pm`
  функциональная приёмка не заметит: план останется прежним, вырастет только
  время. Поэтому эти два места защищены словами здесь, а не случаем стенда;
- создание переменных для заведомо невозможных выплат может вернуть прежнюю
  деградацию времени и памяти.

## Проверка

Функциональная приёмка выполняется через `scripts/check.py --quick` и сквозной
демо-счёт. Для изменений этого механизма в итог задачи записываются время каждой
стадии, общий runtime, статус и значения целей до/после на одном входе.
