# ADR: локальный слой исполнения и развития (harness) для demo-ui

- Статус: принято как архитектурная рамка L0 (FOT-HARNESS-TZ-001, раздел 6 и 9.1);
  части L1 и L2 реализованы; актуальные проверки и долг — в IMPLEMENTATION-STATUS.md
- Дата: 2026-09-11
- Владелец: технический ответственный; предметные решения — владелец продукта

## Контекст

Сервис уже хранит реестр, документы, планы, прогоны и ленту в SQLite
(`app/db.py`), считает планы подпроцессом CLI и держит каталог агентов
словарём в `app/agents.py`. ТЗ требует добавить версии, снимки, решения,
проверки и управляемое развитие способностей, не ломая пользовательский сценарий
и не завися от ПАИШ. Решения ниже фиксируют, *где* это будет жить и *как*
называться, чтобы L1–L4 не спорили об этом заново.

## Решения

**1. Хранилище — та же SQLite плюс неизменяемые артефакты на диске.**
Новые объекты ТЗ (RunManifest, ContextSnapshot, LocalDecision, EvaluationRecord,
Finding и остальные из раздела 6.1) — таблицы в той же базе `app/data/fot.sqlite3`,
добавляемые нумерованными миграциями (`migrations/NNN_*.py` с dry-run и отчётом).
Материальные артефакты — байты входа решателя, результат, фактический контекст
запроса к модели — лежат в `app/data/artifacts/<sha256[:2]>/<sha256>` и
никогда не переписываются; таблицы ссылаются на них по полному SHA-256.
Отдельная база для каждого вида объекта не заводится (ТЗ 6).

**2. Единый локальный service layer — пакет `src/fot_planner/harness_local/`.**
Модули по операциям ТЗ 6.3: `versions` (регистрация и разрешение version ref),
`snapshots` (снимок входа и контекста), `decisions` (LocalDecision с реальным
actor), `runs` (начать/продолжить/отменить с operation ID и версией объекта),
`evaluation` (EvaluationRecord, обязательный набор проверок), `findings`,
`improvement` (candidate, эксперимент, активация, откат). Пакет не импортирует
`app/` и ничего сетевого; `app/main.py` зовёт его, а не наоборот. ПАИШ
подключается только через явный интерфейс `harness_local/adapter.py`
(протокол с методами export/import/status), реализация которого лежит в
отдельном необязательном пакете `paish_adapter` и в основной установке
отсутствует.

**3. Канонический JSON — свой версионированный формат `fot-json-v1`, не JCS.**
`json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"),
allow_nan=False)` в UTF-8 без BOM; NaN/Infinity отклоняются; деньги — строка
десятичного числа с двумя знаками и валютой `{"amount": "160000.00",
"currency": "RUB"}`. Формат честно не является RFC 8785: у JCS свои правила
для чисел и экранирования. Конвертация в JCS — обязанность адаптера на
интеграционной границе, с проверяемым преобразованием. Хеш байтов файла и хеш
канонического JSON — разные величины и хранятся в разных полях.

**4. Версии.** Материальные версии — полный SHA-256 содержимого; выпуск —
SemVer. Короткий SHA-1 подсказок (`app/agents.py::version_of`) остаётся
legacy-меткой `prompt_sha1_7` и не выдаётся за версию способности. Версия
инструмента без модели включает хеш кода (`src/fot_planner/`) и зафиксированный
список зависимостей (`pip freeze` на момент выпуска), а не только имя.

**5. Каталог и схемы.** Описания способностей, процедур, инструментов и
профилей — файлы `capabilities/<key>/<semver>.json`, схемы — `schemas/local-harness/*.schema.json`
(JSON Schema draft 2020-12). Словарь `AGENTS` в `app/agents.py` становится
представлением каталога для интерфейса и генерируется из него однократным
переходом с проверкой эквивалентности (ТЗ 9.1). До этого перехода расхождения
каталога с фактом видны в `docs/requirements-map.json` (проверка к05).

**6. Профили проверки — флаги существующего `scripts/check.py`.** Имена
фиксируются сейчас, реализация — по мере готовности профилей:

| Профиль ТЗ | Команда | Состояние |
| --- | --- | --- |
| local-regression | `check.py --quick` (`--strict` в CI) | есть |
| local-contract | `check.py --contract` | нет: появится с L1 (схемы, версии, повторы на временной БД) |
| local-e2e | `check.py --full` | частично: сквозной счёт без сервиса; перенос и история — L5 |
| capability-evaluation | `check.py --evaluate <experiment>` | нет: L4 |
| paish-contract / paish-live | вне основной установки | I1/I2 |

Машиночитаемый отчёт — `check.py --report`, схема расширяется полями ТЗ 10.2
(ID требования, источник evidence, known-defect ref) без смены имени файла.

**7. Порог производительности (NFR-001).** Baseline — три одинаковых прогона
`scripts/demo_offline.py --limit 240` без модели на одном входе;
свидетельство `docs/evidence/FOT-HARNESS-TZ-001/L0.3-baseline.json`. Порог:
медиана времени решателя после изменения обвязки не хуже медианы baseline
более чем на `max(1 с, 10 %)` при тех же стадиях и настройках. Порог
зафиксирован до реализации L1 и меняется только решением владельца после
измерений.

## Последствия

- Пользовательские маршруты и CLI сохраняются; новые операции идут через
  service layer, старые — переводятся на него по одному, с адаптером
  совместимости.
- Живая база не мигрирует автоматически: миграции запускаются оператором на
  копии, с dry-run и планом возврата (ТЗ 9.2, MIG-002). Стенды продолжают
  ставить `FOT_SKIP_ORPHANS=1`.
- Каталог перестаёт быть источником правды о реализации: правду показывают
  обработчики и карта требований.

## Уточнения реализации

### Уточнение L2.1–L2.2 (13.09.2026)

Реализован узкий каталог `harness_local/catalogue.py`: восемь ролей и одна
цепочка распознавания шаблонной книги. AGENTS генерируется из описаний;
дублировать словарь или тексты процедуры больше нельзя. Схемы runtime —
строгие Pydantic-модели на уже установленной зависимости; их JSON Schema
draft 2020-12 хранится в `schemas/local-harness/`. При расхождении схема
не принимается. Обновление Pydantic с изменённым представлением схем требует
проверки и согласованного обновления файлов, не тихой генерации на старте.

Handler — закрытый ключ, а callable привязывает приложение. Модель не может
передать import-путь, actor или полномочия. Проверяются exact ссылки,
контракты входа/выхода, область и разрешённый файл. Resource availability
пока передаётся сервисом; hard timeout, cancellation, model/domain profiles,
обязательные checks и релизы — следующие части, не реализованные гарантии.
Полный digest описания называется descriptor_digest и не выдаётся за digest
кода со всеми зависимостями. Процесс закрепляет каталог до перезапуска.

Для исправлений переиспользуется LocalDecision: отдельная запись по
subject_kind=правка либо correction_bindings внутри единого решения по
предложениям документа. Binding содержит точный источник, статус и UTC-время;
автор берётся у локального оператора. Это не новая таблица или миграция.
Неизвестные старые связи не восстанавливаются по имени файла. Широкие scope,
полный контекст извлечения и exact Verdict ещё требуют реализации.

### Уточнение L2.3 (14.09.2026)

Снимок контекста извлечения (`harness_local/extraction.py`) хранится в том же
хранилище артефактов по SHA-256 каноническим JSON `fot-json-v1`: байты
документа отдельным артефактом, тексты подсказки, ID применённых и исключённых
исправлений, провайдер и имя модели, тексты и хеши системной подсказки,
параметры вызова, итог ответа. Ключи провайдера в снимок не попадают.
Неизменяемую ревизию модели провайдеры не сообщают — поле `revision` пустое,
ограничение записано рядом (VER-002). Предложение ссылается на снимок;
приговор — на редакцию документа по байтам, предложение и снимок (миграция
006). Стенд разбора воспроизводит проверку по тем же байтам и подсказкам;
имя файла эталоном не является (MEM-003). Отдельные таблицы
ExtractionSnapshot/ContextSnapshot не заводятся: артефакт и ссылка по хешу
достаточны и новых таблиц не требуют.

### Уточнение L2.4 (14.09.2026)

Конфликт исправлений разрешается явным решением оператора: LocalDecision
вида «данные», предмет «конфликт правок», действие с оставленной и
заменёнными правками; заменённые не удаляются и в подсказку не идут, новое
расходящееся значение открывает спор заново (MEM-002).

Проверки результата описаны в каталоге видами `check` и `profile`.
`check` хранит requirement ID (номер карточки свода), правило применимости
словами и доверенный обработчик `audit.<номер>`; исполняемое правило
применимости живёт в `result_audit` под тем же номером. `profile` задаёт
обязательный состав для области; сервис передаёт его решателю флагом
`--require`, решатель печатает состояние каждой проверки. Обязательная
проверка без реализации — not_run и FAIL, не not_applicable (CAP-004).
Catalogue остаётся вне CLI: политика обязательности — у сервиса, исполнение —
у чистого аудита; команда с флагом входит в снимок прогона.

### Уточнение L3 / QA-002 (14.09.2026)

Первый технический блок сохраняет `evaluation_plan` и `evaluation` внутри
артефакта RunManifest схемы 3. Отдельная таблица EvaluationRecord пока не
добавляется: это запись сообщённых solver состояний, а не независимая оценка.
Версии обязательных проверок и SHA-256 описаний закрепляются до вызова;
метод связан с версией кода пакета и его зависимостей из снимка. После
завершения состояния привязаны к хешам входа и конечного выхода. Отсутствующие
измерения помечаются пробелом, а не выводятся из текста статуса.

`reported_verdict=passed` означает только полный положительный протокол
закреплённого набора. `evaluation.verdict` при этом остаётся inconclusive:
отдельное независимое исполнение и повторный аудит преобразованного отчёта
не выполнены. Локальная приёмка — not_run; актуальность — not_checked;
зрелость — not_assessed. Отрицательные/неполные состояния не дают допуска.
Legacy-интерфейс и предметные правила не изменены. Старые снимки читаются
без изменения байтов; новые записываются под новым хешем. Миграции БД нет.

## Оставшиеся решения

Конкретные схемы таблиц, формат instruction-файлов процедур и политику
автоматического включения улучшений (по умолчанию выключено, GOV-002) —
это решения L1, L2 и L4, каждое со своим ADR или карточкой.
