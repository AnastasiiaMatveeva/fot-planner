# Единый список замечаний: контракт и покрытие

## Как работает

`app/static/issues.js` — чистый адаптер и общий HTML-компонент. Вход: снимок отчёта, независимые проверки, сообщения расчёта, версия. Выход: список объектов `id, rule, category, severity, subject, period, metrics[], target, detail`.

`target` содержит раздел, идентификатор строки, исходный номер колонки и месяц. Идентификатор замечания включает версию; индексы строк относятся только к этому снимку. Сортировка и фильтрация таблицы не меняют адрес исходной строки. Переход снимает скрытие строк/колонок, выбирает месяц и выделяет ячейку. Возврат восстанавливает фильтры, период, прокрутку и фокус.

Проверки старого формата без идентификаторов сотрудника/месяца ведут в собственную строку раздела 15. Имена не разбираются регулярными выражениями для угадывания адреса. При отсутствии строки интерфейс явно сообщает об этом. Это честная граница покрытия, а не переход в произвольную таблицу.

## Что прочитано в модели

- `src/fot_planner/optimizer.py`: допустимые назначения, связь суммы оклада с выбранной должностью и открытой ставкой; ручные фиксации; ограничения ставок по строке и человеку; основное место; баланс выплат/потребности и разрешённый дефицит; касса и минимальные остатки; предельное число исполнителей; распределение трудоёмкости и денег; штрафы за отклонения трудоёмкости и изменения плана.
- `src/fot_planner/payroll_rules.py`: точный процент 120 и допустимость источника; связь 122 с окладом; несовместимость 152 с другими надбавками; П2556; приказные выплаты; П4; БЭП; особые условия Приоритета.
- `src/fot_planner/labor_rules.py`: совместимость должностей, месяцы строки, отнесение выплат и трудоёмкости.

Нельзя переносить бытовое описание ограничения вместо кода. В частности, П4 содержит равенство для активированной части и групповое ограничение, а не только индивидуальный верхний порог. Трудоёмкость в оптимизаторе использует штрафуемые отклонения; допустимый дефицит также участвует в оптимизации. Список не объявляет эти ситуации невозможным результатом решателя.

## Адресные переходы

| Источник | Класс | Раздел и адрес |
|---|---|---|
| Остаток/перерасход ФОТ договора | Внимание / ошибка | 2, договор, остаток/выплаты |
| Дефицит из результата | Внимание | 14, строка дефицита, месяц, недоплата |
| Превышение БЭП из отчёта | Ошибка | 8, строка договора/месяца, отклонение |
| Превышение П4 из отчёта | Ошибка | 9, строка сотрудника/месяца, отклонение |
| Отрицательная касса | Ошибка | 4, договор, остаток на конец, месяц |
| Объём/сумма/средняя трудоёмкости вне допуска | Внимание | 10, строка трудоёмкости, соответствующее отклонение |
| Работа вне этапа / превышение числа людей | Ошибка | 10, строка, статус/число людей |
| Остальные независимые проверки | По типу условия | 15, конкретная строка проверки |
| Прочие сообщения расчёта | По уровню сообщения | 15, конкретное сообщение |
| Проверки отсутствуют | Внимание | 15, явное состояние недоступности |

## Границы

Это единый формат отображения доступных результатов проверок, а не новый полный аудитор математической модели. Не все ограничения решателя сейчас имеют отдельную независимую проверку в `app/rules.py`. Приказы, отдельные условия 120/Приоритета, точность ручных фиксаций и все стадии целей требуют отдельных проверок, если нужно подтверждать их независимо от решателя. Доступный контроль П4/БЭП не подтверждает каждое внутреннее равенство payroll-модели. Отсутствие сообщения не является таким подтверждением.

Новый вид контроля добавляется адаптером с явными единицами, серьёзностью и адресом; разметка общего списка не меняется. Старый формат проверок может показывать ту же тему, что и агрегированный отчёт: независимые результаты не удаляются по похожему тексту. Дубли сообщений о неосвоенном остатке устраняются по договору и типу сообщения.

## Проверка и демонстрация

`node scripts/test-issues.cjs` проверяет семь сценариев, стабильные адреса, уровни, границы, фильтры, экранирование, неизменность входных данных, дубли остатков и адреса строк настоящих генераторов таблиц БЭП/П4/трудоёмкости.

`/issues-demo.html` использует тот же `issues.js` и вымышленные данные. Таблицы источников в демонстрации упрощены и явно помечены как тестовые. Они не являются результатом запуска оптимизатора и не изменяют данные организации. В браузере проверены все семь переходов и возврат, отдельно — переход к ячейке остатка настоящего плана и сохранение фильтра.
