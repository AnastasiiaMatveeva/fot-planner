# Работа агентов в fot-planner

Это общий договор для Codex, Claude Code и других агентов, работающих с
репозиторием. Инструкции конкретного инструмента могут дополнять этот файл,
но требования проекта хранятся здесь и в `docs/`.

## С чего начинать

1. Прочитать `docs/README.md` и выбрать канонический документ по задаче.
2. Проверить `git status`; не перезаписывать чужие незавершённые изменения.
3. Для изменения правила сначала обновить карточку требования и проверку,
   затем код.

Локальная память агента вне репозитория не является источником требований.
Полезное правило из такой памяти сначала переносится в канонический документ;
противоречие записывается как открытый вопрос и не разрешается догадкой.

## Куда смотреть по задаче

| Задача | Канонический документ |
| --- | --- |
| расчёт, ограничения, цели | `docs/ПРАВИЛА_РЕШАТЕЛЯ.md` |
| чат и действия модели | `docs/ЧАТ_ПРАВИЛА.md` |
| интерфейс и ручная проверка UI | `docs/ИНТЕРФЕЙС.md` |
| документы экономистов и происхождение данных | `docs/ИСТОЧНИКИ.md` |
| harness, аудит результата, критерии приёмки | `docs/ТЕСТИРОВАНИЕ.md` |
| демо | `docs/ДЕМО.md` |
| перенос на другой компьютер | `docs/ПЕРЕНОС_НА_ДРУГОЙ_ПК.md` |
| постановка нового требования | `docs/ШАБЛОН_ТРЕБОВАНИЯ.md` |

Снимки аудитов и документы с датой в имени объясняют прошлое состояние, но не
переопределяют канонические правила.

## Как вводить новое требование

Для каждого требования нужны:

- устойчивый идентификатор;
- статус: `подтверждено`, `рабочая гипотеза`, `спорно` или `отменено`;
- точная формулировка и источник;
- допустимые и недопустимые примеры;
- место исполнения: валидация входа, модель решателя или интерфейс;
- независимая проверка готового результата, если правило видно в результате;
- положительный и отрицательный случай в harness;
- явная запись пробела покрытия, если какого-то слоя пока нет.

Языковая модель может объяснить уже найденное нарушение, но не должна быть
единственным судьёй числового правила. Проверяемые инварианты реализуются
детерминированно. Образец полной карточки — `RATE-001` в
`docs/ПРАВИЛА_РЕШАТЕЛЯ.md`.

## Приёмка

```bash
.venv/Scripts/python.exe scripts/check.py --changed  # затронутые части
.venv/Scripts/python.exe scripts/check.py --quick    # без сети, около минуты
.venv/Scripts/python.exe scripts/check.py            # плюс разбор документов
.venv/Scripts/python.exe scripts/check.py --full     # плюс сквозной демо-счёт
```

Нельзя сообщать о готовности без проверки, соразмерной изменению. Если красное
не связано с правкой, надо назвать конкретный случай и причину. Разобранный
случай, ожидающий решения человека, временно заносится в
`harness/known_red.txt`; это реестр долга, а не способ сделать ворота зелёными.

`tests/` временно отключены и не являются приёмкой. Текущее устройство и
ограничения проверок описаны в `docs/ТЕСТИРОВАНИЕ.md`.

## Границы

Без прямого разрешения пользователя нельзя:

- удалять планы, прогоны и документы в работающем приложении;
- останавливать чужие процессы и серверы;
- менять `.env` и `data/demo` в день показа;
- изменять `app/data/`: там живая база и загруженные документы;
- скрывать нарушение ослаблением проверки или добавлением необъяснённого
  `known_red`.

Секреты не читаются и не попадают в git. Числа из приказов и справочников
живут в данных с указанием источника, а не в подсказке агента.

## Несколько параллельных задач

Для независимой задачи используется своя ветка или worktree и свой порт.
Перед изменением чужого решения надо прочитать комментарий, карточку требования
и ADR: причина ограничения часто находится там.

## Стиль

Комментарии пишутся по-русски и объясняют причину. В интерфейсе и отчётах —
только данные, заголовки, статусы, легенды и подсказки без пояснительного текста
и повтора уже показанных значений. Реплики, обсуждение и рассуждения агента
остаются только в чате.
